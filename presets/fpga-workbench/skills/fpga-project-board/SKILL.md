# project-board:上板验证

工程一般都要走到上板(除工程根本不部署到硬件)。但**上板是直接操作硬件的动作**:

- **不自行启动**:用户没说要上板,不得因为"该收尾了"就去连板子
- **动手前核实并请用户确认**:器件/编程器、**`bit/` 归档那份**是否对应当前代码、
  `doc/constraints.md` 管脚与电平是否已核过
- **固化(写 Flash)不可逆**:参数必须经用户确认,不得自行推断
- 板子不在手边就做别的;**不得声称上板通过**

| 东西 | 在哪 |
|---|---|
| bit / ltx | **`bit/`** |
| 原理图 | `sch/` |
| 结论 | `doc/board.md` |

其余工程技能按需并列或回跳,见 `fpga-project-spec`。

## 前置(不满足不得上板)

1. **`doc/syssim.md` 是 PASS**(仿真验证已通过)—— **这是硬门槛**,见下节
2. `doc/timing.md` 是 PASS:时序没过,现象不可信
3. `doc/constraints.md` 管脚逐条核过(`sch/` 原理图),错了会损伤板子
4. 有 bit(**`bit/` 归档**,见 `doc/impl.md`),且与当前代码对应

### 仿真没通过,不许上板

**上板前必须确认仿真验证通过。** 不是「大概对」「应该行」——
是 `doc/syssim.md` 里的结论为 `PASS`(工程级联仿)且模块级结论齐。

| 情况 | 能不能上板 |
|---|---|
| 联仿 PASS + 时序 PASS + 管脚核过 | ✅ 可以 |
| 联仿 `UNVERIFIED`(没跑完/覆盖不足) | ❌ **先补仿真** |
| 联仿 `FAIL` | ❌ **先修问题** |
| 时序 `FAIL` | ❌ 先收时序 |
| 管脚未核 | ❌ 先核管脚(会损伤硬件) |

**为什么必须先仿真**:上板调试的成本是仿真的几十倍 —— 没有信号可见性,只能靠改代码、
重新综合、下载,用二分法逼近。**仿真能做的不留到板子上做。**

### 出了问题:先复现,再改,再上板

**不允许不停地上板试找问题。** 每次上板都要满足:

```text
上板发现问题
   ↓
在仿真里复现（必须,否则不知道改得对不对）
   ↓
定位归属：RTL / 测试平台 / 约束 / 实物接线
   ↓
修 —— 修完补测（覆盖率要够，不能只试那一个用例）
   ↓
仿真验证通过
   ↓
才允许二次上板
```

| 阶段 | 要求 |
|---|---|
| **复现** | 在仿真里造出同样的现象;造不出来说明理解还没到,继续查,别急着上板 |
| **定位** | 判断归属(见 `fpga-module-verif` 的差异归属),不要瞎改 |
| **修 + 补测** | 不只是修那一处;补上能覆盖这类问题的用例,**看覆盖率是否够** |
| **回归** | 仿真重跑,原有用例不能倒退 |
| **二次上板** | 只有前面都过了才上 |

**「再烧一次试试」不是调试方法。** 上板次数要能说清每次为什么 ——
说不清就说明还没在桌面侧想明白。

**允许的例外**:只在硬件上才出现的现象(时序裕量、电源、温度、器件特性)。
这类要**先缩小范围**(用 ILA/VIO 抓到具体信号),再判断能否在仿真里构造 ——
**不能构造的要在 `doc/board.md` 写清为什么**,并记录当时抓到的证据。

### 上板前必须过的三项机器检查

这三项都是「仿真里根本看不到、上板才发现」的形态，而且前两项会**损伤硬件**。

**① 引脚与 IO 机器比对(不是人工看)**

```
node project-pin-audit.mjs <工程根> --expect <板级引脚表.csv|.xdc>
```

人工核 200 个引脚必错。脚本逐项比 `PACKAGE_PIN` / `IOSTANDARD` / `DRIVE` / `PULLTYPE`，
并查引脚重复占用。**电平标准不一致是阻塞项**：`LVCMOS18` 配成 `LVCMOS33`
可能把 3.3V 灌进 1.8V 的 bank，直接损伤器件。

期望表两种来源都支持：结构化 CSV/TSV，或上一版工程/板卡例程的 XDC。
两者都没有时脚本会退 2 **明确说缺期望值**，不会假装通过。

**② 配置模式与电源时序**

- **配置模式**确认（JTAG / Master SPI / Slave Serial / BPI）：模式由板上的
  `M[2:0]` 引脚电平决定，写死之前先对着原理图核一遍。选错模式的表现是「下载成功但不启动」。
- **Bank 电压**：每个 bank 的 `VCCO` 必须与分配给它的 IO 标准匹配。混用要在设计阶段就分开。
- **电源时序**：多数 FPGA 要求内核先于 IO 上电（或按手册规定顺序）。上电顺序错会闩锁。
- **配置完成信号**：`DONE` / `INIT_B` 要有可测点，出现「程序跑了但没反应」时先量这两个。

**③ PLL / MMCM 锁定**

`locked` 必须等，不能靠固定延时。判据：复位释放逻辑要**以 `locked` 为条件**，
而不是 `#100; rst_n = 0;`。锁定时间因器件和配置而异（几十微秒到几毫秒），
固定延时在换器件/改参数后就失效。

## 上板分七级(不要一把梭)

首次上板失败最贵的不是"有 bug"，而是"不知道 bug 在哪"。分级能把
「板子完全不工作」拆成「第 N 级不工作」，定位成本从几天降到几小时。

**每一级都有明确通过判据，不通过就停在那级，不许跳到下一级。**

| 级 | 验证内容 | 通过判据 | 失败时优先查 |
|---|---|---|---|
| **L0** | 电源与配置 | `DONE` 拉高；各电源轨电压实测在规格内；静态电流在预期区间 | 配置模式引脚（`M[2:0]`）、配置时钟、上电顺序、比特流是否匹配器件型号 |
| **L1** | 时钟与 PLL | `PLL/MMCM` 锁定信号有效；时钟输出引脚实测频率与设计值一致（误差 < 100 ppm） | 参考时钟是否起振、PLL 参数、时钟输出是否分到测试点 |
| **L2** | 复位释放 | 复位同步释放正常；释放后所有状态机处于 IDLE；各模块复位完成标志有效 | 复位极性、复位同步器结构、复位是否覆盖所有寄存器 |
| **L3** | 寄存器读写 | 通过 JTAG/UART 能正确读写全部寄存器；写后读回一致；只读寄存器返回预期常量 | 地址译码、寄存器位宽、总线时序、读写使能 |
| **L4** | 单通道数据通路 | 选定的一条通道端到端跑通；相关错误计数器保持为 0；trace 显示完整流程 | 握手时序、FIFO 深度、位宽匹配 |
| **L5** | 全通道并行 | 所有通道同时工作；无串扰、无资源争用；各通道错误计数器均为 0 | 仲裁逻辑、共享资源冲突、时钟偏斜 |
| **L6** | 满负载与边界 | 最高速率、最长包、最坏背压下，错误计数器仍为 0 | FIFO 深度不足、背压处理缺陷、时序余量不足 |

> ⚠️ **L0 与 L1 绝不允许跳过**
>
> 这两级成本最低、信息量最大，却最常被「反正之前测过了」跳过。
> 而恰恰是它们能区分「板子根本没起来」和「逻辑有问题」—— 这两种情况的排查路径完全相反。
>
> 跳级的代价：板子不工作时你无法判断是电源、配置、时钟还是逻辑，
> 只能靠反复改代码重新下载来二分。

**L3 之后再说「功能对不对」**。前面几级都过了，问题才可能真的在业务逻辑里。

**每级要提前准备的东西**（上板当天才想起来准备，实际执行时往往就被省掉了）：

| 级 | 提前准备 |
|---|---|
| L0 | 电源测试点位置图；各轨标称值与容差；配置模式跳线设置；比特流与器件型号对应表 |
| L1 | 时钟测试点物理位置；示波器/频率计；各时钟标称频率清单；PLL 锁定信号的观测方式 |
| L2 | 复位信号观测点；各状态机的状态输出寄存器地址；复位完成标志读取脚本 |
| L3 | 寄存器读写脚本；寄存器映射表；每个寄存器的读写测试向量 |

L0–L3 完全可以脚本化，做成开机自检：换板、换比特流都能一键跑，结果可归档对比
「上次是好的，这次坏了」。

### 生成 L0–L3 自检脚本

```
node project-board-selftest.mjs <工程根>
```

生成的 `<工程根>/prj/board_selftest.tcl` 含 L0–L3 四段，用 Vivado Tcl 跑：

```
vivado -mode batch -source prj/board_selftest.tcl
```

**为什么是 Tcl 不是 Python**：指南给的骨架用 `pyjnius` 调 `hw_server`，
而本机没装 pyjnius；`vivado.bat` 与 `hw_server.bat` 都在。
寄存器读写本来就是 Tcl API，绕一层 Python 只是多一个失败点。

**用之前必须做的事**：

1. 把所有 `TODO:` 换成本项目真实的值（**寄存器地址全是占位符**）
2. 确认 hw_server 能连上板子
3. **首次使用请先在真实板子上跑一遍**：这份 Tcl 是按官方 API 写的骨架，
   **没有在本机真机验证过**（本机没接板子，`open_hw_manager` 跑不起来；
   用 ModelSim 的 Tcl 代跑不可行，见工具文件头）

**脚本的判据设计**：任一级 FAIL 就 `exit 1` 停下，不继续后面的级 ——
L0/L1 没过时，后面几级的结果没有意义。

**它检查不了什么**（写清边界，避免误以为都覆盖了）：

| 项 | 为什么脚本做不了 |
|---|---|
| 电源轨实际电压 | 要万用表或板载 ADC：脚本只能读设计里有对应寄存器的通道 |
| 时钟实测频率 | 要示波器/频率计，或板载频率计数寄存器 |
| 配置模式引脚电平 | 硬件跳线，脚本只能读 `DONE` |
| 上电时序 | 要示波器抓多通道 |

这四项**必须人工测**，脚本只负责能自动化的部分。

## 内建可观测性(上板失败时的救命稻草)

上板调试的速度取决于**你能看到什么**，而不是你多聪明。**这是设计输入，写进 SPEC**，
在需求评审时就确定：当作事后补救手段，等于放弃了它 90% 的价值。

- **错误计数器可读回**：每个协议接口、每个 FIFO、每个状态机配一个饱和计数器
  （**饱和不回绕**，否则 65536 次错误会显示成 0），通过寄存器总线可读。
  上板后读一遍就知道哪个模块出问题，不用挂分析仪。
  建议覆盖：协议违例（SLVERR/DECERR/握手超时）、存储边界（FIFO 溢出下溢、地址越界）、
  校验失败（CRC/ECC/包头）、逻辑异常（状态机 default 命中、非法编码）。
- **里程碑 sticky 位**：如「收到第一个包」「完成第一次握手」「进入 RUN 状态」各置一位，
  **只能显式清零**。上板后看这几位就知道流程卡在第几步：这是最快的二分定位手段。
- **片上 trace**：BRAM 里划环形缓冲（时间戳 + 事件码 + 数据），比逻辑分析仪便宜、
  不占探针、能长时间跑、能捕偶发事件。
  **`wrapped` 标志必须有**：为 false 时有效数据是 `0..wr_ptr`，为 true 时全部有效、
  从 `wr_ptr` 开始读才是时间顺序。
- **心跳**：自由运行时钟驱动的计数器，输出到 LED 或寄存器。
  心跳不闪 + 寄存器读不到 → 配置/电源问题；心跳不闪 + JTAG 能连 → 设计没加载或时钟没起；
  心跳闪但业务不工作 → 时钟正常，读里程碑位定位到具体模块。
- **调试逻辑要能关**:ILA / trace 都要有编译开关(如 `` `ifdef DEBUG_BUILD ``),
  量产版本完全移除,避免占资源、影响时序收敛。

### ILA / VIO:改模块,不要加测试端口

**要探的信号在模块内部有,就在那个模块里挂 ILA/VIO,不要为了引出信号新增端口。**

```systemverilog
// ❌ 错:为了调试往端口上引出内部信号
module dma_ctrl (..., output logic [7:0] dbg_state, output logic dbg_fifo_full);

// ✅ 对:在模块内部挂调试核
module dma_ctrl (...);
`ifdef DEBUG_BUILD
  ila_dma u_ila (.clk(clk), .probe0(state), .probe1(fifo_full));
`endif
```

| 要求 | 为什么 |
|---|---|
| **不加调试端口** | 端口是接口契约,加一个就要改 spec、改顶层、改所有例化点;量产时删掉又要改一遍 |
| **`ifdef DEBUG_BUILD` 包住** | 不包住就进量产版本,占资源、拖时序 |
| **探针信号名与模块内实际名字一致** | 改名后 ILA 探的还是旧信号会报 `not found` |

**模块的问题要回模块改**:模块是库里的,在工程里加 `ifdef` 探针会让库与工程两份不一致。
要么把探针写进模块本身(作为模块的可观测性设计),要么在顶层用 ILA 探**已经引出到端口**的信号。

**不要为了测试制造一堆接口**:「先引出来以后好观察」这类理由不成立 ——
需要时再改模块加探针,不需要时一个都不该有。

这一项的成本约占总工时 3–5%，但能把上板调试从「周」压到「天」。

**签署判据**：在不重新综合、不接外部仪器的前提下，能回答三个问题 ——
① 设计当前处于哪个阶段？② 哪个模块出现了异常？③ 异常发生前发生了什么？
三个中任何一个答不出，说明可观测性不足。

## 下载

Vivado 硬件管理器(命令原文记入产物;GUI 亦可,写清点了哪几步):

```
connect_hw_server
open_hw_target
# 设备选择与 templates/programming/vivado_program.tcl 同一套逻辑(读 DEVICE_FILTER)
if {[info exists DEVICE_FILTER] && $DEVICE_FILTER ne ""} {
  set devices [get_hw_devices -filter $DEVICE_FILTER]
} else {
  set devices [get_hw_devices]
}
if {[llength $devices] == 0} {
  error "no hardware device matched; check cable, target, and DEVICE_FILTER"
}
if {[llength $devices] > 1} {
  error "multiple hardware devices matched; set DEVICE_FILTER explicitly (e.g. NAME =~ \"*xc7a100t*\")"
}
set device [lindex $devices 0]
current_hw_device $device
refresh_hw_device -update_hw_probes false [current_hw_device]
set_property PROGRAM.FILE {bit/<顶层>.bit} [current_hw_device]
program_hw_devices [current_hw_device]
```

- **确认下载成功**:看输出与器件 `DONE`;要做配置回读用
  `readback_hw_device -force -file <回读文件> [current_hw_device]`,再与 bit 比对
- **不要用不存在的选项**:`program_hw_devices` **没有 `-verify`**;`verify_hw_devices` 是
  eFUSE 加密器件用的,不是通用回读
- 有 ILA/VIO 时用 `bit/<顶层>.ltx`;看波形用已确认脚本起仿真 GUI(见 `fpga-project-syssim`)

## 固化到 Flash(需要掉电保持时)

```
write_cfgmem -force -format MCS -size <容量MB> -interface <SPIx4|BPIx16> \
  -loadbit "up 0x0 bit/<顶层>.bit" <mcs 路径>
```

`-size` / `-interface` 必须与板上 Flash 一致(`sch/` / 手册)—— **写错会损坏 Flash**,不确定就问。

## 判据分两层

**第一层:观察。** ILA/VIO 波形符合预期(握手成对、数据不丢、状态机对)。记触发与文件路径。

**第二层:实测。** 回读数据与 golden 比对一致：这才是**证据**。写法不同而取值等价不算错,
但必须真转成同一口径比过(见 `fpga-module-verif`)。

**人工观察**(相机/示波器/肉眼)单独记,标明人工,**不进自动判据**。

## 判据

- **PASS**:两层都过(波形符合 + 回读一致)
- **FAIL**:数据不一致 / 握手卡死 / 输出不对
- **BLOCKED**:板子连不上、cable/驱动、bit 与器件不匹配
- **UNVERIFIED**:只完成下载或观察,尚未执行足够的实测与独立比对
- **NOT_APPLICABLE**:**只有**工程根本不部署到硬件;没有板子记 `BLOCKED`,不能当 N/A
- 判定词含义见 `fpga-module-verif` 的**状态表**(唯一权威)

**上板轮次要写进报告**:每次上板记「为什么这一次上板、前一次的问题怎么复现与修复的」。
**连续多次上板却说不清每次的动机,就是「不停地上板试」** —— 那不算调试方法。

## 产物

写 `<用户指定工程目录>/doc/board.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)+ 板子/器件 + **`bit/` 路径**(哪次实现)
- **上板前的仿真状态**:`doc/syssim.md` 的结论 + 模块级结论是否齐(上板门槛)
- **上板轮次记录**:第几次、为什么这次上板、前一次的问题怎么复现与修复的
- 下载命令原文 + 成功依据(DONE / 回读路径)
- ILA/VIO:信号、触发、波形路径、所见
- 实测:回读文件 + 与 golden 比对结论
- 人工观察项(标明人工)
- 没验到的部分**写出来**;新文件同步 `doc/files.md`
