# module-rtl:编写、编译检查与规范核对

本环节把**已确认的规格**(路径 A)或**本次修改要求**(路径 B)落成 RTL,分三步:起文件并写逻辑 →
编译器检查 → 逐条核对规范。**三样都写完之后再跑检查**(为什么,见「本环节要跑的命令」)。

## 两条适用路径(先判走哪条)

判据是**任务风险**,不是"有没有新增功能"(完整判据的唯一出处是 `AGENTS.fpga.md` / 包内 README
的 `fpga-mode-rules` 第 2 条,这里只引用):

| 路径 | 什么时候走 | 要不要先有图 / 规格 |
|---|---|---|
| **A. 新设计 / 重大变更** | 重大架构、公共接口、跨时钟方案、关键数据通路、用户可见的算法决策**尚未确定** | 要先有已确认的 `spec/spec.md` 与 `spec/flow.md`(实现思路流程图),按图写 |
| **B. 局部调查与修复** | 改语法错、处理单条 lint / 编译告警、已有模块的局部 Bug、已有批准方案里的普通实现 | **不要求**先建 `spec/flow.md`、不要求先批准流程图、也不要求先补一整套规格 |

**路径 B 只要求三件事**:读相关代码与项目约束(有 `spec/` 就读,没有**不要现补一套**)、最小必要
修改、改完跑与本次改动相关的那两项检查(聚焦验证)。**不要为局部修复去建 `spec/flow.md` 或补规格**;
反过来说,**路径 A 不许跳过图**。

两条路径共用下面三步(起文件 → 编译检查 → 逐条核对规范):**路径 B 跳过第一步的「起文件」**
(改的是已有文件,没有要起的新文件),差别还在于"依据读到什么程度",见「前置」。

写什么不是自由发挥 —— **路径 A** 依据三份东西(**路径 B** 有哪份读哪份):

| 依据 | 取什么 |
|---|---|
| `spec/spec.md` | 端口、位宽、时钟与复位、验收判据(AC)、指标(吞吐 / 延迟 / 反压) |
| `spec/flow.md` | **实现路径**:数据通路、状态机跳转、握手与反压、时钟域、流水级数与拍数 |
| `spec/spec.md` 的「参考资料」一节 | 算法、参数取值、定点位宽 —— 有原型或文档就照它,别凭感觉 |

**路径 A 里,图与规格就是"怎么做"的定稿。** 实现中发现图走不通、或规格没写清:先跟用户说清,
回去改 `spec/flow.md` / `spec/spec.md` 并重新确认,再接着写 —— **不要默默换一条路径自己写下去**,
那样的代码没人能对着图复核。

## 前置

1. **先判走哪条路径**(见开头那张表);拿不准时按风险判 —— 卡住的是**重大决策**就走路径 A
2. 找约定文件 `.fpga-workbench.json`(模块根;路径 A 找不到时询问用户,见 `fpga-module-spec`);
   **路径 B 找不到锚点不阻塞、也不作为问用户的理由** —— 直接读相关代码与项目约定
3. **按路径读依据**:
   - 路径 A:读齐三份 —— `spec/spec.md`、`spec/flow.md`、以及 spec 里点名的参考资料(原型 / 文档)
   - 路径 B:**有哪份读哪份**,加上相关源码与项目约定(接口以**已有工程的实际情况**为准)
4. **缺规格文件 ≠ 缺关键决策依据**:没有 `spec/` / `flow.md` **不阻塞**路径 B 的局部任务;只有
   接口、位宽、复位极性与事件沿、时序口径、算法参数这些**影响结果**的决策在代码与项目约定里都
   定不下来时,才回去问用户 —— 缺文件本身不是问的理由,也不要自己拍板定
5. 待查源码按设置里选定的 RTL 语言取:`rtl/` 下的 `.sv` / `.v`(递归)。
   源码为 VHDL 时本检查器不覆盖 → 结论记 `NOT_APPLICABLE` 并说明原因,**不得视为通过**
   (判定词含义见 `fpga-module-verif` 的状态表,唯一权威)

## 第一步:用模板生成文件(**仅新建文件时**),再编写逻辑

**仅新建文件时走这一步**:不要从空文件写起,也不要手抄模板。用自带命令把模板复制成目标文件
(命令名就是环节:`module-rtl-new`);**路径 B 改已有文件时跳过这里,直接在原文件上改**:

```powershell
node "<自带命令目录>\module\module-rtl-new.mjs" <模块根> <模块名> --template "<RTL 模板路径>"
```

- 模板路径取设置里配好的那份(见会话开头「本机 FPGA 工具链」的模板一节;留空即插件自带那套)
- 落点固定为 `rtl/<模块名>.<模板扩展名>`;要另换位置用 `--out`
- **脚本只替模块名**(`<ModuleName>` / `<module_snake>`),其余内容原样保留 —— 模板千差万别,
  日期、作者、版本这些按模板自己的规矩来,不要靠脚本替
- 要写的语言没有对应模板时(自带模板是 SystemVerilog 的),照它的**结构**自己起一份 ——
  这种情形没有可复制的模板,脚本用不上

### 编写时自己把住

**模板已经定好的不要再另立一套**:文件头字段、开头/结尾那些指令、端口声明与对齐、
`end else begin` 同行、九个小节 banner 及其排法 —— 复制模板时就带过来了,照模板即可。
第三步的机械检查会查它们(所以不是"不用管",而是"不必在这里再抄一遍");换了模板以模板为准。

下面这些模板定不了,写的时候就守住:

- **(仅路径 A)接口照 `spec/spec.md` 抄准**:端口名、方向、位宽、复位极性、时钟;
  路径 B 以**已有工程的实际情况**为准,缺规格文件本身不是问用户的理由
- **(仅路径 A)实现路径照 `spec/flow.md`**:数据通路与流水级数、状态机、握手与反压、跨时钟处理按图里定的来
- **(仅路径 A)算法与参数照「参考资料」**(原型跑出来的参数、定点位宽、边界处理);
  **没有参考就问用户**,不要凭感觉定关键参数
- 复位与事件沿**以实际工程为准**:模板默认高有效复位(`if (rst)`),新写代码照模板即可 —— 模板
  自己的代码里别写成 `rst_n`、`!rst` 或 `negedge rst`。**已有工程按它实际的接口与项目约定来**;
  要改复位极性或事件沿,**必须先说明理由并取得确认**
- `always_ff` 用 `posedge`:**新代码照模板**,已有工程以它现有的时钟沿约定为准
- 每个 RTL 须有设计断言,并写明 Purpose / Trigger / Failure
- **一个 always 块内不混放不相关信号** —— 除非共用同一套控制逻辑(同一状态机、同一事务生命周期、
  同一寄存器组)。无法说明其共同控制关系时拆分
- 写测试平台时(`verif/` 下,见 `fpga-module-verif`)须含 `$fatal` / `$error`:
  仿真失败须能被自动捕获,不得依赖人工观察波形
- 模板里没替的占位符(如 `<DATE>` / `<Author>`)按本模块的实际情况填上;各 `TODO` 换成真实逻辑

### 一个模块拆多个文件时

- **什么时候拆**:一个文件写不完整块逻辑时就拆,拆成子模块。**判据是功能,不是代码行数**
  —— 看 `spec/flow.md` 那张图里有几个功能块:图上是几块,就应该是几个模块;一个文件能写清楚的,
  不为"模块化"硬拆
- **每个子模块一个文件**:文件名 = 模块名(与 `module <名字>` 一致),都平级放 `rtl/` 下
- **现成的子模块**:**先问用户**——由用户提供,还是由本环节编写?不得自行假定,也不得另行实现
  一个替代:
  - 用户提供 → 直接使用(放 `rtl/` 下,与自己的代码同等对待);**来源与版本**写进 spec 的
    「参考资料」,便于后续比对与上板核对
  - 本环节编写 → 按本环节的规矩写,同样放 `rtl/`
  - **不得为绕开依赖而重写现成的子模块**
- 顶层(本模块若是个小系统)与子模块平级:`rtl/<模块名>.<扩展名>` + `rtl/<子模块名>.<扩展名>`
- `rtl/ip/` 只放外来代码(厂商 IP、他人提供的模块),自己的代码不放进去

### 需要 IP 核时:先问用户,再按用途归位

1. **先问用户**:该 IP 由本环节生成,还是由用户提供?不得自行假定,也不得另行实现一个绕过它
2. **由本环节生成**:
   - 逻辑简单(一个小 FIFO、一个计数器之类)→ 直接在 `rtl/` 里编写,不走厂商 IP 流程
   - 厂商 IP → 用工具生成(如 Vivado 的 `create_ip` + `generate_target`),**生成脚本与 `.xci`
     一并入档**以保证可复现,不得只在图形界面点出来
3. **用户提供** → 按下面的规则归位,来源与版本写进 spec 的「参考资料」

归位规则(生成完或拿到后按用途拆开):

- **仿真用的文件**(仿真模型、厂商仿真库、行为级模型)→ `verif/`
- **RTL 与综合用的部分**(RTL 封装 / wrapper、本环节编写的那部分、`.xci`)→ `rtl/ip/`

同一个 IP 可能同时出现在两处:`verif/` 放仿真模型,`rtl/ip/` 放综合用的实体。归位后在
`rtl/lint.md` 或 spec 里记一句走了哪条路(自建 / 用户提供),便于后续比对与上板核对型号与版本。

## 第二步:编译器检查

**用设置中选定的编译器。** 会话开头「本机 FPGA 工具链」已写明是哪个工具、路径是什么,并给出该工具
的调用姿势 —— 按那个姿势执行,下文以 Verilator 为例:

```powershell
& "<编译器路径>" --lint-only -Wall --top-module <顶层模块名> <文件...>
```

- 只查 `rtl/` 下的源码(递归);`verif/` 下的仿真模型与测试平台不参与本检查
- 拆了子模块就**多个文件**:被例化的在前,按层级自底向上排(与仿真那节同一条)——
  顺序错了会报"找不到模块",那不是代码写错
- 报 `module not found`、而该模块来自 IP(只有 `.xci` 或加密模型,没有可检查的 HDL)属正常现象:
  把该 IP 的端口 wrapper 一并传入,或**优先用 IP 自带的 `*_stub.v`**(就在 `rtl/ip/` 下,原地不动)。
  确实没有自带的那份、必须生成时,**生成物也要落回该 IP 目录下**
  (`rtl/ip/<ip名>/<ip名>_stub.v`,用脚本生成即可,例如 `write_verilog -mode synth_stub`),
  **不许放到别处** —— 仿真的 `run.do` 只跳过 `rtl/ip/` 下的 `*_stub.*`,放到别处就会和真模型同名打架。
  **不得为通过检查而改动端口**
- 告警须清零;确需压制时在源码内**就地豁免**(`/* verilator lint_off XXX */` …
  `/* verilator lint_on XXX */`)并注明原因。**禁止用 `-Wno-XXX` 全局屏蔽**

## 第三步:逐条核对规范

**格式以模板为准**(见会话开头「本机 FPGA 工具链」的模板一节;未提供即插件自带那份),
核对前先读模板。

**机械部分先跑自带命令**(路径见会话开头「本模式自带的命令」):

```powershell
node "<自带命令目录>\module\module-rtl-check.mjs" <模块目录>
```

覆盖文件头、九个小节块、端口类型、复位极性、always_ff、end/else、断言、制表符、行尾、代码行非英文、
测试平台自检,并给出**行号**。要结构化结果时加 `--json`(平时不用加)。

工具判不了、只能读代码判的,对照下面三类:

- **格式类(机械可判)**:禁用制表符;代码行限英文(注释除外);行尾统一,单个文件内不得混用
- **与依据一致**:端口对 `spec/spec.md`;实现路径对 `spec/flow.md`;参数取值对「参考资料」。
  不一致就在这里说清为什么
- **结构类(须读代码判定)**:一个 always 块内混放不相关信号、断言是否正确、命名与结构

**外来代码另行判断**:放在 `rtl/ip/` 下的厂商 IP 与他人模块,机械检查**跳过**(它们不按本模块的
格式规范书写)。这类代码的报错先与用户确认是否要改,**不得擅自重排厂商代码**。

## 本环节要跑的命令

**时机:三步都写完之后跑,不逐文件跑。** 一次编译要展开全部文件,逐文件运行等于把同一次编译拆成
很多次;报错集中在一轮里定位与修改,也比来回切文件快。

| 对应 | 命令 | 看什么 |
|---|---|---|
| 第二步 | `& "<编译器路径>" --lint-only -Wall --top-module <顶层模块名> <文件...>` | error / warning,判法见第二步 |
| 第三步 | `node "<自带命令目录>\module\module-rtl-check.mjs" <模块目录>` | 退出码与带行号的条目,判法见第三步 |

- `module-rtl-check` 会顺带查一眼 `verif/tb_*` —— 所以"这一轮全绿"包含测试平台的机械规范,
  **第一次跑仿真前那部分也该是干净的**
- 退出码 0 = 无阻塞项 / 1 = 有阻塞项 / 2 = 用法或环境问题(如 `rtl/` 下没有源码、纯 VHDL 不在
  检查范围内)。**2 不是通过**:按前置第 5 条如实记 `BLOCKED` 或 `NOT_APPLICABLE` 并说明原因
- **一次就够**:全绿就写结论收工;有 FAIL 或告警就定位、修改,再重跑,直到干净
- 例外两条(就是**路径 B** 的聚焦验证):排查具体报错时可以只查该文件或该条告警;下游(仿真失败、
  综合报错)回头补查本环节时,目的是修问题,不是"补齐流程"
- 本检查**不构成关卡**:正在排查仿真问题时,不必停下补 lint

## 产物

写 `<模块根>/rtl/lint.md`(报告与 RTL 同目录:`rtl/` 既是源码目录,也放本环节的检查结论)。内容:

- **结论**:`PASS` / `FAIL` / `BLOCKED` / `NOT_APPLICABLE`
- 执行过的**命令原文**(可直接复现),**两条命令的完整输出都记进来**
- 编译器报的 error / warning 逐条处理:改了哪里,或就地豁免的理由
- 逐条规范的核对结果;未通过项写清 `文件:行`
- `BLOCKED`:编译器未就绪(设置里标「未就绪」)→ 如实说明并停止,**不得声称已执行**
- `NOT_APPLICABLE`:`rtl/` 下无源码,或源码为 VHDL(本检查器仅覆盖 SystemVerilog / Verilog)
- 判定词的含意见 `fpga-module-verif` 的**状态表**(唯一权威);本环节只写"哪种情况记哪个词"

结论与证据均须可追溯。**未做本检查即进入仿真,等于把问题推到下游。**

## 出口:什么时候算写完

四条都满足才算本环节结束,否则如实标出缺哪条(不要写成"应该没问题"):

1. 与依据一致(路径 A:端口照 `spec/spec.md`、路径照 `spec/flow.md`、参数照「参考资料」;
   路径 B:与相关代码和项目约束一致,改动没有跑出本次问题的范围)
2. `module-rtl-check` 跑过,且 `rtl/lint.md` 里的 `结论:` 不是 FAIL
3. 编译告警清零,或每条都有就地豁免的理由
4. 没做完的地方明确留在代码里(如某个子模块先留 `TODO`),并在结论里点出来

达标后把结论写进 `rtl/lint.md`,下一步交给验证环节(测试平台用 `module-verif-new.mjs` 起)。
