# module-rtl:编写、编译检查与规范核对

把已确认规格(路径 A)或局部修改要求(路径 B)落成 RTL:起文件与写逻辑 → 编译检查 → 规范核对。

## 两条适用路径

按任务风险选择;判据见 `presets/fpga-workbench/workspace/AGENTS.fpga.md` 第 2 条
(骨架复制为 `AGENTS.fpga.md`)。

| 路径 | 什么时候走 | 要读什么 |
|---|---|---|
| **A. 新设计 / 重大变更** | 架构、公共接口、CDC、关键数据通路或用户可见算法尚未确定 | 先确认 `spec/spec.md` 与 `spec/flow.md`(缺图不得开工) |
| **B. 局部修复** | 语法、单条告警、局部 Bug、已批准方案内的普通实现 | 有哪份读哪份;缺规格不阻塞 |

**两条路径共用编译与规范检查;路径 B 跳过「起文件」。**

**局部路径(路径 B)不要求先建 `spec/flow.md`,也不要求先批准流程图** —— 缺规格文件不阻塞,
直接读相关源码与工程约定;路径 A 才要求先有图。

依据取什么:

| 依据 | 取什么 |
|---|---|
| `spec/spec.md` | 接口、时钟复位、AC 与性能指标 |
| `spec/flow.md` | 数据通路、状态机、握手、CDC 与拍数 |
| spec 的「参考资料」 | 算法、参数和定点位宽 |

路径 A 若发现图走不通或规格不清,先说明并修改 `spec/flow.md` / `spec/spec.md` 后继续;
不得默默换实现路径。

## 前置

1. 从 `.fpga-workbench.json` 找模块根。路径 B 找不到锚点不阻塞,直接读相关源码与工程约定
2. 只有缺**关键决策依据**(接口、复位/事件沿、时序、算法参数无法从现状确定)时才问用户
3. 按设置所选语言读 `rtl/` 下 `.sv` / `.v`。源码为 VHDL 时本检查器不覆盖 →
   记 `NOT_APPLICABLE` 并说明原因,**不得视为通过**

## 第一步:起文件与写逻辑(仅新建时起文件)

**路径 B 改已有文件时跳过起文件。** 不要手抄模板:

```powershell
node "<自带命令目录>\module\module-rtl-new.mjs" <模块根> <模块名> --template "<RTL 模板路径>"
```

模板取设置值,默认落 `rtl/<模块名>.<模板扩展名>`;`--out` 可指定其它位置(相对模块根)。
脚本只替模块名;无对应语言模板时沿用现有模板结构手工起文件。

### 编写时自己把住

**模板已定好的照模板即可**,不要另立一套(文件头、指令、端口对齐、`end else begin` 同行、
九个小节 banner)。机械检查会查它们;换了模板以模板为准。

**模板管不了的,写的时候守住**:

- **(路径 A)依据三处**:端口/时钟复位照 `spec/spec.md`、实现路径照 `spec/flow.md`、
  算法参数照「参考资料」。**没有参考就问用户**,不凭感觉定关键参数
- **(路径 B)** 以已有工程的实际情况为准,缺规格文件本身不是问用户的理由
- **一个 always 块内不混放不相关信号**：除非共用同一套控制逻辑(同一状态机、同一事务生命周期、
  同一寄存器组)。无法说明共同控制关系时拆分
- 写测试平台时(`verif/` 下)须含 `$fatal` / `$error`:仿真失败要能自动捕获,不靠人看波形
- 模板里的 `<DATE>` / `<Author>` 等占位符按实际填上;`TODO` 换成真实逻辑

**具体写法规则(复位、位宽、字面量、命名、latch、非阻塞、驱动源、断言等)全在
[RTL 规范清单](references/rtl-style-and-checks.md)**,本节不重复。

### 跨时钟域与复位

**只要设计里有一个以上时钟域,或用到异步复位,就必须读** [跨时钟域与复位](references/cdc-and-reset.md)。

**为什么不在仿真里查**:仿真器把两级同步器建模成「延迟两拍、输出一定正确」,
把复位释放建模成同一时刻的确定事件。跑多少激励都不可能复现亚稳态。

### 一个模块拆多个文件时

- **什么时候拆**:一个文件写不完整块逻辑时就拆,拆成子模块。**判据是功能,不是代码行数**。
  看 `spec/flow.md` 那张图里有几个功能块:图上是几块,就应该是几个模块;一个文件能写清楚的,
  不为"模块化"硬拆
- **每个子模块一个文件**:文件名 = 模块名(与 `module <名字>` 一致),都平级放 `rtl/` 下
- **现成的子模块**:**先问用户**——由用户提供,还是由本环节编写?不得自行假定,也不得另行实现
  一个替代:
  - 用户提供 → 直接使用(放 `rtl/` 下,与自己的代码同等对待);**来源与版本**写进 spec 的
    「参考资料」,便于后续比对与上板核对
  - 本环节编写 → 按本环节的规矩写,同样放 `rtl/`
  - **不得为绕开依赖而重写现成的子模块**
- 顶层(本模块若是个小系统)与子模块平级:`rtl/<模块名>.<扩展名>` + `rtl/<子模块名>.<扩展名>`
- `rtl/ip/` 只放外来代码(厂商 IP、他人提供的模块),自己的代码不放进去


### IP / XPM 与时序实测

引入、替换或接手厂商原语、XPM、厂商 IP 前，必须先读 [IP / XPM 选型、归位与时序卡](references/ip-and-timing.md)。其中规定了选型顺序、生成方式、文件归位，以及 `timing.json` 的实测要求。

## 第二步:编译器检查

执行前读 [RTL 规范清单](references/rtl-style-and-checks.md) 的**附录「三个检查工具」**,
按当前语言、工具与厂商库选命令。编译不通过先修正,再进第三步。

Verilator 补的是 `vlog` 不报的那一类(`UNUSEDSIGNAL` / `UNDRIVEN` / `WIDTHTRUNC` /
`LATCH` / `CASEINCOMPLETE` 等)—— **须逐条判定,不得整体忽略**。

## 第三步:逐条核对规范

先跑机械检查(见附录「机械检查覆盖什么」),再按 [RTL 规范清单](references/rtl-style-and-checks.md)
的**信号定义 / 命名 / 排版 / 写法**逐条对照代码。不得只凭肉眼跳过确定性检查。

## 本环节要跑的命令

**时机:写完再统一跑,不逐文件。** 一次编译展开全部文件;逐文件跑等于把同一次编译拆成多次。

| 对应 | 命令 |
|---|---|
| 第二步 | `node "<自带命令目录>\module\module-rtl-lint.mjs" <模块根>` |
| 第三步 | `node "<自带命令目录>\module\module-rtl-check.mjs" <模块目录>` |

**为什么 lint 用这条命令而不直接敲 verilator**:Windows 上 Verilator 是 msys2 包,直接调报
「找不到 `verilated_std.sv`」;命令固定走 bash,没 bash 退 3(BLOCKED)。
细节见 [RTL 规范清单](references/rtl-style-and-checks.md) 附录。

**退出码**:0 = 无阻塞项 / 1 = 有阻塞项 / 2 = 用法或环境问题(`rtl/` 无源码、纯 VHDL)。
**2 不是通过**：如实记 `BLOCKED` 或 `NOT_APPLICABLE`。

**`module-rtl-check` 会顺带查 `verif/tb_*`**：所以"全绿"包含测试平台的机械规范,
第一次跑仿真前那部分也该干净。

**跑几遍**:全绿就收工;有 FAIL 或告警就改再跑,直到干净。**不是关卡** ——
查具体报错时可只查该文件或该条告警;下游(仿真失败、综合报错)回头补查时目的是修问题,
不是"补齐流程"。

## 产物

写 `<模块根>/rtl/lint.md`(报告与 RTL 同目录:`rtl/` 既是源码目录,也放本环节的检查结论)。内容:

- **结论**:`PASS` / `FAIL` / `BLOCKED` / `NOT_APPLICABLE`
- 执行过的**命令原文**(可直接复现),**两条命令的完整输出都记进来**
- 编译器报的 error / warning 逐条处理:改了哪里,或就地豁免的理由
- 逐条规范的核对结果;未通过项写清 `文件:行`
- `BLOCKED`:编译器未就绪(设置里标「未就绪」)→ **不得声称已执行**;可以继续给出分析与**未验证的**修复(工作区规则第 6 条),但结论必须写明未验证(不是"停止不动")
- `NOT_APPLICABLE`:`rtl/` 下无源码,或源码为 VHDL(本检查器仅覆盖 SystemVerilog / Verilog)
- 判定词的含意见 `fpga-module-verif` 的**状态表**(唯一权威);本环节只写"哪种情况记哪个词"

结论与证据均须可追溯。**未做本检查即进入仿真,等于把问题推到下游。**

## 出口:什么时候算写完

四条都满足才算本环节结束,否则如实标出缺哪条(不要写成"应该没问题"):

1. 与依据一致(路径 A:端口照 `spec/spec.md`、路径照 `spec/flow.md`、参数照「参考资料」;
   路径 B:与相关代码和项目约束一致,改动没有跑出本次问题的范围)
2. `module-rtl-check` 跑过,且 `rtl/lint.md` 里的 `结论:` 不是 FAIL
3. 编译告警清零,或每条都有就地豁免的理由
4. 没做完的地方明确留在代码里(如某个子模块先留 `TODO`),并在结论里点出来

达标后把结论写进 `rtl/lint.md`,下一步交给验证环节(测试平台用 `module-verif-new.mjs` 起)。
