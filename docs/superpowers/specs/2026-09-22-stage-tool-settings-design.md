# FPGA 开发模式：按环节配置工具的设置重构设计

状态：待用户审阅

日期：2026-09-22

范围：只修改插件设置、设置页、兼容迁移、会话工具解析和相关自检；不读取或修改 `presets/**/skills/`。

## 1. 目标

把当前“一套全局脚本 / 编译 / 仿真 / 综合工具”的设置模型改为三层：

1. **通用工具**：登记这台机器实际安装的工具和路径，一种工具保留一个独立路径。
2. **模块工具**：按模块开发的五个环节选择首选工具，并允许为某个环节覆盖通用路径。
3. **工程工具**：按工程开发的八个环节选择首选工具，并允许为某个环节覆盖通用路径。

这些设置表达的是“当前环节可用什么能力”，不是阶段状态机，也不规定执行顺序。模块五个环节仍可按任务反复切换；工程环节同样不形成自动流水线。

## 2. 现有实现中需要修正的点

现有设置已经有几项值得保留的基础：设置值一次性原子保存、未保存值可预演状态、异步请求有代际保护、路径在宿主侧检查、旧键有幂等迁移、字段由服务端元数据驱动渲染。这些不重写。

真正需要修的是数据模型：

- `compilerPath`、`simulatorPath`、`synthesizerPath` 每类只有一个槽位。切换 Verilator / Icarus、ModelSim / XSim、Vivado / Quartus 时，页面会清空或替换同一字段，无法同时保存多套安装路径。
- `compiler`、`simulator`、`synthesizer` 是全局选择。模块 RTL、模块验证、工程集成、系统仿真、实现、时序、上板等环节只能被迫共用同一选择，无法表达环节差异。
- 当前 `option.needs -> pathField` 和客户端 `changeTool()` 都建立在“一组选项只对应一个共享路径”的前提上，不能直接扩展成按环节配置。
- `required + skips` 只会给出全局“缺这个会跳过哪些步骤”，不能准确回答“哪个环节绑定了哪个工具、有效路径来自哪里、为什么当前不可用”。
- “其他工具”只保存路径，没有名称或调用说明，却可能被判成可用；会话端无法据此可靠调用，容易产生假就绪。
- Quartus 虽然可选，但当前设置自己也注明只有路径和探测能力。新模型必须把“检测到路径”和“该环节已有完整支持”分开显示，不能把前者包装成后者。
- 现有自检大量绑定字段总数、固定分组顺序和旧键名。重构时应改成语义断言，否则以后增加一个工具就会造成大面积无意义改动。

## 3. 设计原则

- **登记与选择分离**：通用区回答“机器上有什么”，环节区回答“这个环节优先用什么”。
- **不限制 AI 判断**：每个环节默认选择“由 AI 根据任务判断”。它不是自动选择脚本，而是把已登记工具作为环境事实交给 AI，由 AI 根据工程、目标和证据选用。
- **显式选择优先**：用户为环节选定工具后，AI 应优先采用；若工程事实不允许，应说明原因再调整，而不是暗中换工具。
- **路径可覆盖但不复制**：环节路径留空时使用通用路径；只有同一工具在某个环节确实需要另一安装或包装入口时才填写覆盖路径。
- **`不用` 与 `自动判断` 不同**：`none` 表示用户明确禁用；`auto` 表示未指定首选，由 AI 在通用工具中判断。
- **设置是能力地图，不是流水线**：状态页不得显示“当前阶段 / 下一阶段 / 已完成百分比”，提示词也不得要求按顺序推进。
- **保留用户数据**：迁移只补新字段，不覆盖非空的新字段；旧的自定义工具路径也必须有落点。
- **迁移只运行一代**：用隐藏的 `settingsModelVersion` 标记模型版本，避免用户以后主动改回 `auto` 时又被旧值反向覆盖。

## 4. 数据模型

### 4.1 工具目录

在 `lib/toolchain.js` 中建立单一 `TOOL_CATALOG`，每个工具声明：标识、类别、显示名、通用路径字段、路径类型、支持的能力、探测规则和调用提示。设置、检测、状态和会话提示都从这里派生，避免四份名单漂移。

内置工具：

| 类别 | 工具 | 通用路径字段 | 路径类型 |
|---|---|---|---|
| 脚本 | Python 3 | `pythonPath` | 文件 |
| 编译 | Verilator | `verilatorPath` | 文件 |
| 编译 | Icarus Verilog | `iverilogPath` | 文件 |
| 仿真 | ModelSim / Questa | `modelsimPath` | 文件 |
| 仿真 | Vivado XSim | `xsimPath` | 目录 |
| FPGA 套件 | Vivado | `vivadoPath` | 文件 |
| FPGA 套件 | Quartus Prime | `quartusPath` | 文件 |

保留三类自定义槽位，以兼容旧的“其他”选择：

- `customCompilerName`、`customCompilerPath`、`customCompilerNotes`
- `customSimulatorName`、`customSimulatorPath`、`customSimulatorNotes`
- `customFpgaToolName`、`customFpgaToolPath`、`customFpgaToolNotes`

自定义工具有有效路径时只标为“路径可用”；说明为空时不得宣称已有固定调用配方。AI 可根据实际项目、工具帮助或用户说明判断用法。

语言标准、`modelsim.ini` 和六个模板路径继续保留，在“通用工具”下作为“语言与库映射”“模板”子组，不复制到每个环节。

### 4.2 环节绑定

每个绑定由两个字符串字段组成：

- `<binding>Tool`：`auto`、该类别的具体工具、`custom-*` 或 `none`。
- `<binding>Path`：可选的环节专用路径；留空使用工具目录中的通用路径。

路径解析优先级固定为：

1. 当前环节非空的覆盖路径；
2. 所选工具的通用路径；
3. 未配置。

`auto` 不静态解析成某一个工具，也不自动改写设置；会话提示提供可用通用工具，由 AI 在当前任务中判断。`none` 则明确标记本绑定不使用外部工具。

模块工具的五张环节卡：

| 环节 | 可配置绑定 |
|---|---|
| 规格 | 脚本工具（可选） |
| RTL | 编译 / lint 工具 |
| 验证 | 仿真工具、脚本工具（参考模型与比对） |
| 综合 | FPGA 套件 |
| 审查 | 不新增独立工具；按审查对象复用以上绑定，并在界面明确说明 |

工程工具的八张环节卡：

| 环节 | 可配置绑定 |
|---|---|
| 规格 | 脚本工具（可选） |
| 集成 | 编译 / elaboration 工具、FPGA 套件 |
| 约束 | FPGA 套件 |
| 系统仿真 | 仿真工具、脚本工具 |
| 实现 | FPGA 套件 |
| 时序 | FPGA 套件 |
| 上板 | FPGA 套件 |
| 发布 | FPGA 套件（用于重建 / 复核时可选） |

一个阶段可以配置多个“角色”，但设置不触发任何执行，也不把这些角色串成流水线。

### 4.3 字段元数据

扁平的 `FIELDS` 仍作为 DSH 设置 schema 和查询白名单，新增以下展示元数据：

- `section`：`common`、`module`、`project`
- `sectionLabel`：通用工具、模块工具、工程工具
- `stage` / `stageLabel`：环节卡标识与标题；通用字段为空
- `advanced`：环节覆盖路径为 `true`
- `bindingKey`：覆盖路径受哪个工具选择控制

客户端按 `section -> stage -> field` 渲染。覆盖路径默认收在“高级：本环节单独覆盖路径”中；选择 `auto` 或 `none` 时不显示无意义的覆盖输入框。

## 5. 状态与界面行为

设置页只有三个顶层区块：通用工具、模块工具、工程工具。

通用工具区：

- 每个工具独立保存路径，切换任何环节选择都不得清空这里的值。
- “检测本机工具”把候选写入对应的工具专属字段，不再写入通用的 `compilerPath` 一类共享槽位。
- XSim 继续使用目录选择，其余已知工具按各自元数据选择文件或目录。

模块 / 工程工具区：

- 每个环节是一张独立卡片；字段标签显示角色，而不是暗示步骤顺序。
- 状态显示“自动判断”“明确不用”或“工具名 + 有效路径 + 路径来源（通用 / 环节覆盖）”。
- 路径不存在时，只标记相应绑定不可用；不把整个 FPGA 模式判为不可用。
- Quartus 的路径可用状态与流程支持提示分开。界面继续明确说明当前插件仅保证路径与探测，不虚构完整工程能力。
- 保存继续使用一次 `scope.mutate()` 原子提交；放弃修改、预演状态、浏览请求和检测请求的防竞态逻辑继续保留。

## 6. 旧配置迁移

迁移函数以隐藏的 `settingsModelVersion` 为门槛，完成后写为 `2`；版本已经是 `2` 时返回空补丁。这样迁移保持幂等，也不会在用户以后主动修改新设置时重新介入。规则如下：

1. `verilatorPath`、`modelsimPath`、`vivadoPath` 是更早版本留下的工具专属键，含义正好符合新通用工具区；本次直接把它们提升为可见字段，保留原值，不迁走也不清空。
2. 新的工具专属字段非空时永远保留；当前版本的共享路径只在目标为空时迁入：
   - `compiler=verilator`：`compilerPath -> verilatorPath`
   - `compiler=iverilog`：`compilerPath -> iverilogPath`
   - `simulator=modelsim`：`simulatorPath -> modelsimPath`
   - `simulator=xsim`：`simulatorPath -> xsimPath`
   - `synthesizer=vivado`：`synthesizerPath -> vivadoPath`
   - `synthesizer=quartus`：`synthesizerPath -> quartusPath`
3. 若共享路径存在但旧选择键没有持久化，则按旧默认值迁移（编译器为 Verilator、仿真器为 ModelSim、综合器为 Vivado）；若路径名明确指向另一已知工具，则以路径名和路径类型的可验证特征为准。无法可靠识别的落入相应自定义槽位，不猜成某个厂商工具。
4. 旧选择为 `other` 时，路径迁入相应自定义槽位，名称默认“旧配置中的其他工具”，说明注明来源。
5. 有实际旧配置证据时，旧全局选择复制为相关环节的显式首选，以维持升级前行为：编译器用于模块 RTL 与工程集成，仿真器用于模块验证与工程系统仿真，综合器用于模块综合及工程集成 / 约束 / 实现 / 时序 / 上板 / 发布，Python 用于规格、验证和系统仿真的脚本绑定。
6. 旧选择为 `none` 时，相应绑定迁为 `none`；没有旧路径或显式旧选择的新安装保持 `auto`。
7. `compiler` / `compilerPath`、`simulator` / `simulatorPath`、`synthesizer` / `synthesizerPath` 和旧的 `python` 选择键继续隐藏保留一个兼容周期；迁移成功后清空这些来源键，防止以后反向复活。`pythonPath` 直接作为新通用字段保留。

迁移日志只报告迁移了哪些类别，不打印用户路径。

## 7. 会话提示

`describeEnv()` 改为输出两部分：

1. **可用工具清单**：只列路径存在的通用工具，以及自定义工具的名称 / 路径 / 用户说明。
2. **环节偏好**：分别列模块与工程各环节的绑定、有效路径来源和不可用原因。

提示开头明确写：这是可反复切换的能力配置，不是执行顺序。`auto` 表示由 AI 根据当前任务判断；显式工具表示首选；`none` 表示不使用。提示不生成命令队列、不自动调用工具，也不因某环节缺失而阻止其他环节工作。

## 8. 实现边界

预计只改：

- `lib/toolchain.js`：工具目录、字段、解析、迁移、状态、检测、提示。
- `lib/client.js`：三层 / 环节卡渲染、覆盖路径交互、检测结果落点。
- `lib/index.js`：继续从 `FIELDS` 生成 schema；必要时只调整迁移与状态载荷接线。
- `tools/check-toolchain.mjs` 及确有需要的插件加载自检：验证新设置语义。
- README 中仅与“插件设置如何配置”直接相关的说明（若现有文字失真）。

明确不改：

- `presets/**/skills/**`
- 各环节技能的工作方法、报告格式或判断标准
- 阶段目录和脚手架行为
- 自动执行、自动推进、阶段状态机或流水线

## 9. 验证标准

实现时先补失败测试，再改代码。至少覆盖：

- Verilator 与 Icarus、ModelSim 与 XSim、Vivado 与 Quartus 的通用路径可同时保存，互不覆盖。
- 每个环节可独立选择 `auto`、具体工具、自定义工具和 `none`。
- 有效路径严格遵守“环节覆盖 > 通用路径 > 未配置”。
- XSim 在通用区和环节覆盖区都按目录校验。
- 切换环节工具不修改通用路径，也不修改其他环节。
- 旧配置全部按上表迁移；重复运行迁移不产生新补丁；新值优先。
- 自定义工具没有调用说明时不被描述为已有固定配方。
- Quartus 不因路径存在就被描述成已具备完整工程流程。
- 会话提示明确“非流水线”，并正确区分 `auto` 与 `none`。
- 设置页仍然原子保存，未保存预演和异步请求防竞态继续通过。
- 测试改为按关键字段、环节和行为断言，不依赖一个容易失效的字段总数。
- 完整运行 `npm test` 与 `npm run test:safety`；不通过安装 / 同步命令改动用户环境。

## 10. 验收结果

完成后，用户应能在同一页面：

- 先登记本机所有可用工具；
- 再为模块和工程的各个环节分别指定首选工具；
- 仅在需要时填写环节专用路径；
- 清楚看到每个环节最终采用哪个路径以及为什么可用 / 不可用；
- 保留 AI 针对实际任务选择工具、反复切换环节的空间，不被设置模型推成自动流水线。
