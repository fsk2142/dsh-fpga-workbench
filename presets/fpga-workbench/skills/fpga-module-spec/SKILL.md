# module-spec:讨论与规格

本环节只确定需求与实现路径,不写 RTL。下面五步是**讨论的顺序,不是问卷**:每步锁定一项结论;
信息不足就问,用户也无法提供时记录缺口,不得代为假设。可查资料、读现有工程或写探索原型,
但探索结果不是正式证据。

## 沟通方式

- 每次围绕一项结论问一到两个问题,依据回答继续;不要一次抛出整张清单
- 已有约定或工程事实直接采用;不确定时先复述理解请用户纠正
- 用 FPGA 术语和短句,不造选项、不让用户填表

## 第一步:确定开发方向(模块 / 工程)

**要定下来的**:本次是单个可复用模块,还是整机、顶层或板级工程。

- 模块 → 继续本技能
- 工程 → 转 `fpga-project-spec`,在那里确定模块清单、连接、器件工程与 IP 策略

未说明就问。再用 glob 查找 `**/.fpga-workbench.json`:找到就读并以其目录为模块根;找不到就询问
模块根,收尾时用脚本建骨架。锚点内容为 `kind: module`、`spec: spec/spec.md`;模块根固定含
`spec/`、`rtl/`、`verif/`、`synth/`,探索产物放 `spec/explore/`,审查报告放 `<模块根>/review.md`。

**注意**:路径必须在对话与规格中记录,不要靠推断。

## 第二步:确定器件

**要定下来的**:目标器件与封装;器件决定原语、IP、资源估算、约束和 RTL 写法。

- 模块属于已有工程且工程有 `doc/spec.md` → 以工程 spec 为唯一来源,模块 spec 只写“器件见工程 spec”
- 独立交付模块 → 在模块 spec 写型号、系列与封装

**注意**:已有事实直接采用;暂时未定可继续讨论,但须记录“器件待定”及影响,不要拖到写 RTL 时再定。

## 第三步:讨论方案

**要定下来的**:功能、接口、指标与实现参考。

先定一句话功能、输入/输出及正确标准、上下游和时钟复位来源,再谈协议、位宽、吞吐、延迟、反压与
资源预期。

### 先建立参考,再确定方案

- 有资料 → 读取规格书、厂商文档、论文或既有实现,只提取本模块所需的数字与约束
- 无资料或算法不确定 → 询问是否用 Python 原型验证算法、参数、定点位宽与边界;用户不需要时在
  spec 记录“无参考”

把资料路径、对照数据、参数和取值依据写进 spec 的“参考资料”;探索脚本及中间数据放
`spec/explore/`,文件名前缀 `explore_`。原型同时供 **RTL** 取算法与参数、供**验证**生成独立参考模型
或 golden;参考模型不得照抄 RTL。

**注意**:探索运行本身不作为证据。正式结论须在对应环节重新运行并保存输出;接口或判据变更须先问用户。

## 第四步:画实现思路流程图

**要定下来的**:经用户确认的数据通路、状态机、握手与反压、跨时钟位置、流水拍数及存储结构。

用 Mermaid 写入 `<模块根>/spec/flow.md`,并在对话中贴出。单图 5~15 个节点;节点写中文与信号名,
关键边标位宽、拍数和时钟。复杂设计拆主流程与关键子流程。

```mermaid
flowchart LR
  IN["输入 din / valid"] --> CORE["处理流水 / N 拍"]
  CORE --> OUT["输出 dout / ready"]
```

将图交用户确认。图未确认即方案未确认;用户要求修改或实现中发现不可行时,先更新图再继续。

**注意**:局部 bug 与参数调整无需补图;数据结构、算法路径、状态机或握手时序变化须同步更新。

## 第五步:明确验证要求与对照数据

**要定下来的**:测试平台怎么搭、输入数据从哪来、拿什么对照、如何比对与通过。

- **测试平台**:激励、检查点、日志/波形/数据文件及超时机制
- **输入数据**:实测采集、算法生成、厂商样例或定向边界数据
- **对照数据**:用户 golden、既有实现输出或第三步的独立 Python 原型
- **比对**:`hex_words` / `text_exact` / `binary_exact` / `custom`,以及逐拍/逐项粒度和容差

用户已有数据就**请用户提供**路径、格式与规模;没有则由**本环节确定**激励和独立判据并写明理由。
纯直通等确实无可比行为才记 `NOT_APPLICABLE`;拿不到判据记 `UNVERIFIED`,缺工具或输入记 `BLOCKED`。

**注意**:输入来源与期望值来源都要写明,不得用输入冒充期望。有效样本为 0 不得判 `PASS`;
格式、字节序、位宽或文件头不清时先问。

## 清单(自查用,不作为表单提交)

- 功能边界、接口、协议、位宽、时钟、复位、异常行为与性能指标
- 器件来源、参考资料、流程图和关键参数
- `AC-001`…逐条可自动检查。**拍数/延迟类判据要写成拍数**,如“接收后第 N 拍”;只比对数值、
  不比对时机的判据挡不住时序错位
- 验证方案须写测试平台、激励、独立参考、比对格式、样本要求和通过标准
- 是否需要综合、目标频率和是否上板

## 产物与收尾

1. 用脚本一次建骨架,先 `--dry-run`:

   ```
   node "<自带命令目录>\setup-scaffold.mjs" <模块根> --kind module
   ```

   脚本幂等;已有锚点不覆盖(`--force` 才重建),也不生成空报告。
2. 写 `<模块根>/spec/spec.md`,先记 `spec_state: draft`,确认后改 `confirmed`。
3. 将 Mermaid 本体单独写入 `spec/flow.md`,spec 只引用它,不要存两份。

重大架构、公共接口、跨时钟方案、关键数据通路、用户可见算法决策和正式规格冻结须先确认。
唯一判据见 `presets/fpga-workbench/workspace/AGENTS.fpga.md` 第 2 条;骨架会原样复制为 `AGENTS.fpga.md`。

局部 bug、语法或单条告警不重走规格流程:读取已有资料后按 `fpga-module-rtl` 路径 B 处理;缺少
`spec.md` 或 `flow.md` 本身不阻塞,只有关键决策确实不明时才回来讨论。后续环节只读规格与流程图;
需要改变就回本技能更新并确认。

## 必须询问用户的情形

- 需求有两种合理解释,或两条实现路径代价不同
- 需要改变接口、判据、器件或关键算法参数
- 只有用户能提供文档、输入、golden,或决定是否综合/上板

## 出口

`spec_state: confirmed`、流程图确认且清单齐全 → 可进入实现或其它按需环节。
关键输入仍缺 → `BLOCKED`,在 spec 列出缺项与所需输入。
