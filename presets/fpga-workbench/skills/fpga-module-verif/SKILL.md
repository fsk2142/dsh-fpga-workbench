# module-verif:验证(跑出数据 → 独立比对 → 判归属)

**验证 = 跑一遍 + 用独立参照判对错。** 测试平台只负责把数据跑出来,它证明不了数据是对的;
"对不对"要由**独立于 DUT 的参照**判定。参照可以是**文件**(参考模型 / golden 逐项比对),
也可以是**独立的检查手段** —— 独立 scoreboard、断言与协议检查、定向用例:

- **文件比对**(有 golden 时首选):逐拍 / 逐字节比,不一致为零才算过
- **无文件比对时**(FIFO、UART、握手与控制逻辑这类常常如此):用独立 scoreboard / 断言 /
  协议检查 / 定向用例判定 —— **独立性与有效检查仍是底线,判 PASS 的判据与文件比对同一条**
  (见「判据」):不得拿 DUT 输出当期望、不得覆盖不足或 0 个有效样本就说通过、
  不得只看波形主观判断通过

**确实本来就不适用(有明确设计依据,如模块本来就无可验证的行为)才记 `NOT_APPLICABLE`**;
拿不出判据是 `UNVERIFIED`,不是 N/A —— 两者不能混为一谈(也不是"没有 golden 就不适用")。

**判对错是本环节自己的职责**:跑完先自行比对、自行确认;不一致时判断问题在 RTL、测试平台还是
参照物,改掉重跑。反复确认不了再请用户协助,**不得放着不一致往下走,也不得改判据绕过**。

## 前置

1. 找约定文件 `.fpga-workbench.json`(模块根);找不到则询问用户,见 `fpga-module-spec`
2. 读 `spec/spec.md`:接口、时钟、AC,以及验证方案 —— **比对输入路径、输出路径、格式**三项在其中;
   测试平台与参考模型都照着它写
3. **spec 里若做过 Python 原型**(`spec/explore/` 下,spec 的「参考资料」一节点名了它):
   它是参考模型 / golden 的首选来源(按算法写的,天然独立于 RTL)
4. spec 声明**没有文件比对**、而模块也没有可独立检查的行为 → 本环节才是 **NOT_APPLICABLE**。
   没有 golden 但有断言 / 协议检查 / 定向用例时**不是不适用** —— 用下面那套独立检查手段做,
   并在结论里写清用了哪种
5. **建议**先看 `rtl/lint.md` 是不是 PASS —— 但正在排查验证问题时不必停下补 lint

**没有测试平台 ≠ 本环节"不适用"**:当前目标就是验证功能时,记 `UNVERIFIED`,缺工具记
`BLOCKED`;只有模块本来就没有可验证的行为才算 `NOT_APPLICABLE`。

## 第一步:写测试平台(起文件靠命令,不手抄)

```
node "<自带命令目录>\module\module-verif-new.mjs" <模块根> <模块名> --template "<测试平台模板路径>"
```

默认落 `verif/tb_<snake>.sv`(`<snake>` 是模块名的下划线形式:`UartRx` → `tb_uart_rx`;脚本只替
模块名,要另换位置用 `--out`)。扩展名跟着模板走:先在设置里选对**仿真语言**
(SystemVerilog → `.sv` / Verilog → `.v` / VHDL → `.vhd`)。

测试平台必须满足三条(写法自带 `tb.sv` 里都有,这里只写判据):

- **失败留下可搜的标记**:判定用 `$fatal(1, ...)`,产生 `** Fatal:` 行。只 `$display` 一句 FAIL
  脚本搜不到,这条是硬红线(`$fatal` 不会让 vsim 退出码变非零,见「判据」)
- **判定能自动做**:每处不符 `$error(...)` 并累计,不靠人看波形判断通过与否
- **超时有人管**:没有看门狗,挂死的仿真会一直挂着

结构化自检(握手成对、不出现 X、计数器不溢出、不死锁)写在测试平台里;**数据对不对不在这里判**。

## 第二步:跑出来(全程命令行,不弹图形界面)

下面的例子按 **SystemVerilog**(`.sv`)写;选了 Verilog / VHDL 就把扩展名换成 `.v` / `.vhd`,
编译命令也换成对应语言的形式(`vcom` 对应 VHDL,`vlog`/`xvlog -sv` 对应 SV)。

**先用设置里选定的仿真器** —— 看会话开头「本机 FPGA 工具链」的**已就绪清单**:仿真器是
ModelSim / Vivado XSim / Verilator、路径是什么,都写在那里。**不得另行挑选一个。**

**ModelSim / Questa(默认)**

`run -all`、`quit -f` 是**仿真器自己的命令**,不是 shell 命令 —— 写进 `verif/run.do`,再一次调用。

**别手抄 `run.do`**:用模板起一份(它把踩过的坑固化了,起完按工程改):

```powershell
node "<预设>/tools/module/module-verif-new.mjs" <模块根> --kind run-do
cd <模块根>/verif
& "<仿真器路径>" -c -do "do run.do; quit -f"
```

模板里这几段**别删**(删了就退回"看着跑完了、其实没跑"的形态):

- 收集时**跳过 `rtl/ip/` 下的 `*_stub.*`**:IP 自带的黑盒 stub 与真模型**同名**,放它进编译会
  **静默覆盖真模型**(vlog 只给 Warning),整轮仿真跑在空模块上还打印成功标记;跳过了要打印出来。
- 编译用 `catch` 判定,失败即 `quit -f -code 1`;
- **`onfinish stop` 必须在 elaborate 之后**,否则 `$finish`/`$fatal` 直接结束会话,后面全成死代码;
- 结尾的 **run-level gate** 扫 `sim.log`:有 `Error`/`Fatal` 或缺成功标记 → `-code 1`。

**判据:跑 `run.do` 的退出码说了算** —— 但要知道它为什么可信:裸 `vsim` 的退出码**不可信**
(实测 2020.4:`$fatal` 之后 `run -all` 既不抛错也不改退出码,退出码仍是 0),是**模板里的 gate**
把它变成可靠判据的。**没有 gate 的脚本不能按退出码判。**

- 想清库重跑:`vdel` 要先判一下 `if {[file exists work]} { catch {vdel -lib work -all} }` ——
  裸的 `vdel` 在没有 work 库时会报错并中止整个脚本、而退出码仍是 0(表现为"已跑过",实际什么都没跑)

**Vivado XSim**(选了它就用 Vivado bin 目录下的这三个命令)

```powershell
# Vivado 系的工具同样要写用户目录(%APPDATA%\Xilinx\xsim 等,在工作区外):
# 先重定向再跑,省掉"每次都要放行一次"(原理与实测证据见 fpga-module-synth 的「为什么」)
$env:APPDATA = "<模块根>\verif\.xsim-user"
New-Item -ItemType Directory -Force -Path $env:APPDATA | Out-Null
cd <模块根>/verif
xvlog -sv ../rtl/<源码...> tb_<snake>.sv
xelab -debug typical tb_<模块名> -s tb_sim
xsim tb_sim -runall
```

只写各仿真器**通用**的几条(各工具自己的坑写在该选项的说明里,见会话开头的调用姿势):

- **编译顺序:被例化的在前**,按层级自底向上排;顺序错了会报未解析的模块
- 多个测试平台**一个平台一个进程**跑(`tb_sub_*` → 其余 `tb_*` → `tb_top_*`),`$finish` 结束一个进程

## 厂商原语仿真:先查库映射,别先怀疑 RTL

用到 `IBUF` / `BUFG` / `FDRE` 这类厂商原语、或 IP 核的仿真模型时,下面四条是**实测**出来的
(ModelSim 2020.4 + Vivado 2025.2 的库),照做,不要自己推:

1. **`-L` 接的是「库名」,不是目录** —— `vlog -L unisims_ver` / `vsim -L unisims_ver` 对;
   写绝对路径就报 `Unable to find library` 或 `Module 'IBUF' is not defined`。
   库名从哪来:`modelsim.ini` 的 `[Library]` 段(`库名 = 目录`,一行一条;本机那份在
   ModelSim 安装目录下,几百条映射指向厂商**编译好的**库)。
2. **编译与仿真两头都要带 `-L`** —— 只给 `vsim` 不给 `vlog`,照样报未定义。
3. **带 GSR(全局置位)的原语要配 `glbl`**,而且仿真必须**跑过 GSR 释放**(标准 `glbl.v`
   是 100 ns)。没跑过去会看到"寄存器恒 0" —— 那是**假象**,不得据此判成设计错。
4. **`modelsim.ini` 的搜索顺序**:`MODELSIM` 环境变量 → **当前目录的 `modelsim.ini`** →
   安装目录那份。工作目录里若冒出一份(工具生成的、从别处拷来的),它会**盖掉**安装目录
   那份,表现是"库突然全找不到"而那份 ini 单看没毛病 —— 先看有没有这个文件,再怀疑别的。

**XPM 宏同属这条路**:`xpm_fifo_*` / `xpm_cdc_*` / `xpm_memory_*` 在 **`xpm`** 库里 ——
`vlog -L xpm` / `vsim -L xpm`。本机的 `modelsim.ini`(路径见会话开头「本机 FPGA 工具链」的库映射项)
`[Library]` 段里**通常已经有** `xpm = <…>/xpm` 这条,指向一份**早先编译好的**库:`vmap xpm`
核一下,在就直接用,**不要重编**。只有"映射对、库也在、却仍报未定义(同上面
`Module 'IBUF' is not defined` 那种)"这种硬问题,才退到**用原厂源码自己编一份** —— Vivado 安装
目录 `data/ip/xpm/**` 下的 `.sv`(或用它的 `compile_simlib`),编完在结论里写清用的是哪一份。
**这是退路,不是首选动作**。

**"库"和"映射"是两件事**:编译好的库是东西本身(每个库目录里有 ModelSim 的 `_info` 标记),
`modelsim.ini` 只是"名字 → 目录"的表;缺哪个都跑不起来,但**哪个都不该由本环节去重建**。
自己新编的库(`work`)默认就建在当前目录(而且 `work` 这一条也是可以在 ini 里被映射走的)——
**动手前先跑一次 `vmap work` 看它到底落在哪**,不要假定它在 `verif/work`。

## 输出数据:格式是红线

比对数据写到 `spec` 里确认过的路径与格式,**不得自行改文件名或后缀**。
(这是"按 spec 落盘"的红线;反过来,对方给的 golden 只是**写法**与 spec 不同、取值等价,
不算错 —— 见第四步「格式对不上不代表数据错」。)

写十六进制要写**大写文本**:`$fwrite`/`$fdisplay` **不许用 `%x` / `%h`** —— 用 `%c` 加 ASCII 运算拼字符
(模板里有 `upnib` 函数)。比对按文本逐字节比,`%x` 的宽度与对齐不受控。

**仿真模型**(厂商原语、行为级模型、加密模型)放 `verif/` 下,用**真实的**那一份,不得用简化版或
桩模型顶上 —— 仿真用桩、综合用真 RTL,两边行为不一致时结论不可信。

**测试平台里的延迟/复位拍数照 IP 卡来,别照印象写**:`rtl/ip/<ip>/timing.json`(见
`fpga-module-rtl` 的「IP 时序卡」)记的是**实测**出来的读/写延迟与复位占用拍。测试平台里若把这些
数字写死(比如"等 n 拍再比"),那个 n 必须来自卡;卡上没有的,先补测再写 —— 猜出来的拍数会让
仿真与 RTL 一起错,而仿真还是绿的。

## 第三步:看波形(用户要看时)

批处理只留日志与数据文件,人工排查需要波形窗口。**用已经确认过的 `verif/run.do` 起 GUI**
(XSim 用 `xelab` 起好的那个 snapshot 起 GUI)—— 库映射、源码集合与顶层都由那份脚本决定,
另起一次手工加载必然少编东西。**不要在 `verif/` 里直接开 GUI 加载设计**:TB 在时刻 0 会以
写方式打开它的 dump 文件,光是加载设计就会把那几个文件清零。

- 需要**文本形态**波形(写进报告或供模型读取)用工具自带的 `wlf2vcd`:
  `wlf2vcd -o verif/dump.vcd verif/vsim.wlf`,只保留需要的区间
- 波形是**排查手段**,不是结论:看到的现象要落回 `verif/verif.md` 的结论与归属判断

## 第四步:比对(拿独立参照)

1. 参考模型按**同一批输入**算出期望值
2. 与 DUT 输出逐词 / 逐字节比对
3. **不一致的位置全部列出**,不只报第一个
4. 有差异 → 先判归属,再动代码

### 参考模型必须独立(本环节唯一的硬要求)

- **不许** import RTL、仿真输出、生成的 IP,或任何实现细节
- 从 spec 描述的行为写起,不是从 RTL 抄起 —— 抄 RTL 的模型只能证明"它等于它自己"
- 跑之前先自查两条:模型**不得改写输入样本**;**不得把输入直接当输出返回**
- 宁可让比对**停住**,也不拿输入当期望、然后报"通过"

**参考模型通常就是 spec 里的 Python 原型**(spec 的「参考资料」一节点名了它):它按算法写、
天然独立于 RTL,正好符合上述几条。原型没做过 → 现按算法补一个,**不得照 RTL 的写法去凑**。

### 三种比对格式

| 格式 | 期望值谁出 | 用在 |
|---|---|---|
| `hex_words` | 整数词比对(逐拍 / 逐字) | 整数流 |
| `text_exact` / `binary_exact` | 参考模型给出期望字节 | 文本或二进制逐字节 |
| `custom` | 模块自己的比对器 | 上面都不合适 |

### 差异归属(最易出错之处)

- 差在**固定偏移或固定拍数** → 多为流水线延迟未对齐,不是逻辑错误
- 只差开头或结尾几拍 → 复位没放净、使能或首尾握手
- 整体差一倍、或位宽对不上 → 格式或符号位问题
- 模型改写了输入、或直接返回输入 → **独立性问题**,先修模型,其余不谈
- 全部一致但**样本数为 0** → 根本没比上,不得当作通过

归属判完再动代码:**RTL 错改 RTL,测试平台错改测试平台,模型错改模型**,改完重跑。两边不一致时
两边都可能错,**不得把"参考模型这么算"写成"RTL 是对的"**。

**格式对不上不代表数据错 —— 先看数据是否等价,别在格式上反复纠缠:**

- **表示形式不同**(十六进制 / 十进制、大小写、分隔符、行尾、列序、每行几个词)而数值逐个等价
  → **功能正确**,记一句"格式与 spec 表述不同,数据等价"即可,不阻塞通过、不必为此回头追问
- **能确定取值等价就直接转换后比**(读进来转成同一个口径),不要因为两边写法不同就判 FAIL
- **比对前先归一化,只比值**:行尾(**CRLF 与 LF 是同一份数据的两种写法**)、行尾空白、首尾空白、
  十六进制大小写与 `0x` 前缀 —— 这些差异**先抹平再比**。实测踩过:金标是 CRLF、本工具输出是 LF,
  逐字节比导致**每一行都"不一致"**,一个纯排版差异冒充了功能失败、还被升成了阻塞。
- **格式差异永不单独判 FAIL / 阻塞**:归一化之后**取值**不同才是 FAIL;归一化之前的差异只在报告里
  记一句"格式差异(已归一)",不改变结论、不挡流程。
- 但**必须实际比过再放过**:没有转成同一口径、没逐个对上就说"只是格式问题",等于没验
- **只有取值真的不同才算 FAIL** —— 宽度少一位、符号或字节序不同导致**数值变了**、丢掉某个通道,
  这些看着像格式,实际是功能问题,不得当格式放过

**比对脚本用自带模板 `templates/comp.py` 起一份**(它已经做到了"先归一化、只比值"):

```powershell
node "<自带命令目录>\module\module-verif-new.mjs" <模块根> --kind comp
python verif/comp.py <参照文件> <输出文件> [--kind hex|text]
```

固定落 `verif/comp.py`(文件名不跟模板扩展名走,也不替模块名;已存在不覆盖,`--force` 才覆盖)
—— 取值一致退 0、不一致退 1 并指出位置、读不到退 2。

**自己无法判定数据是否等价时再问用户**,尤其是:

- 文件头、每行几个数、单位这些**不认识**,读不出全部样本(此时连"数据对不对"都还没开始比)
- 拿不准**是否逐拍比、容差多少**(浮点 / 定点截断、允许几拍延迟)—— 口径错了会把正常实现判成
  FAIL,或把真错判成通过
- 用户那份 golden **来路或版本不明**(哪次生成的、是否与当前 spec 同版)

提问时把事实摆齐:哪两个文件、第几拍开始不一致、倾向哪种解释。**不得为推进而自行改比对口径**
—— 判据一松,后续结论都不作数。

**同一处不一致反复出现或判不出归属时同样问用户**,问法相同;不得放着不管,也不得改判据绕过。

## 状态判定(唯一权威)

**判定词只有这一份定义** —— 人设、工作区规则、其它技能提到这些词时都引这张表,不再各自复述:

| 状态 | 含义(唯一权威) |
|---|---|
| `PASS` | 对**适用判据**执行了充分验证,并且有证据 |
| `FAIL` | 执行了有效检查,并且观察到**真实不符** |
| `BLOCKED` | 缺工具 / 依赖 / 权限 / 输入,无法继续 |
| `UNVERIFIED` | 尚未执行,或**证据 / 覆盖不足**(没有 golden 又建立不出独立判据,通常落在这里) |
| `NOT_APPLICABLE` | 有明确的设计依据说明该项检查**确实不适用**;**不得用来掩盖"无法验证"** |

**零样本不等于 `PASS`。** `comp.py` 这类脚本报"比较结果相等"只是**数据层事实** —— 两边都空、
0 个样本时它照样退 0 说"相等"。**脚本判"相等" ≠ 验证 `PASS`**:有效样本是否存在、AC 覆盖到
哪些、判据是否适用,由本技能按上面的定义判 —— **样本数为 0 一律不得判 `PASS`**。

## 判据

**判成败靠日志与比对结果,不是退出码**:ModelSim 批处理下 `$fatal` 之后退出码仍是 0(实测),
"退出码 0 = 通过"对**裸 `vsim`** 不成立 —— 所以 `run.do` 里的 gate 负责把日志条目变成退出码:
**跑 `run.do` 拿到的退出码才是判据**(没有 gate 的脚本不能这么判)。

本环节的**适用判据**,以及各自落在哪个状态(状态定义见上面那张唯一权威的表):

- `PASS`:**独立判据**(文件比对,或独立 scoreboard / 断言与协议检查 / 定向用例)**已执行且覆盖充分**
  —— 走文件比对时要求样本取值逐个等价、**样本数 > 0**;同时测试平台跑出成功标记(模板里是
  `ALL TESTS PASSED (err_cnt=0)`)、日志无 `** Error:` / `** Fatal:` / `TB TIMEOUT`
  (双方只是写法不同、取值等价时先转换再比,不为格式卡住)
- `FAIL`:测试平台挂了(`** Error:` / `** Fatal:` / 超时,或无成功标记),或比对存在不一致
  (给出数量与位置)
- `BLOCKED`:仿真器没就绪、参考模型没实现、输入文件缺失、输出文件没生成;也包括**退出码非零
  且日志无仿真结果**(Tcl 级错误:源文件打不开、编译失败、脚本写错)
- `UNVERIFIED`:`verif/` 下还没有测试平台(`tb_*`),或样本数为 0 / 覆盖不足 —— 如实记这个,
  不要写成通过
- `NOT_APPLICABLE`:有明确的设计依据说明该模块**确实不适用**(本来就无可验证的行为);
  **拿不出判据 / 手段是 `UNVERIFIED`,不是 N/A**

挂死或超时时先查:时钟没起、复位没放、握手没接上、位宽对错。**不得第一反应就调大看门狗。**

## 产物

写 `<模块根>/verif/verif.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)
- 跑过的**命令原文**(或该 `run.do` 的路径),可直接复制复现
- PASS 时:成功标记那一行原文
- FAIL 时:错误列表 + 日志路径 + **归属判断**(RTL / 测试平台 / 模型)+ 改了什么
- 输入 / 输出 / 格式(**照 spec**,改了要说明原因)
- 用了哪种判定手段:文件比对(样本数 + 不一致数与位置 + 参考模型版本)/ 独立 scoreboard /
  断言与协议检查 / 定向用例;差异多时附头几个不一致的上下文
- 覆盖了哪些 AC、哪些没覆盖(未覆盖写"未覆盖",不得写"应该没问题")

**报告里引用的每个路径都要真的在** —— 写 `PASS` 之前跑一次证据路径校验:

```
node "<自带命令目录>\module\module-report-check.mjs" <模块根>
```

它核三件事:① `spec/spec.md` 里 **AC 行声明的证据位置**是否真的存在(模块已经写出结论时,不存在就是
FAIL);② `verif/*.md` / `synth/*.md` 里引用的路径是否都在(缺了 → FAIL);③ 报告里**记过摘要**的依据
内容变没变(变了 → 告警:报告写完之后那份依据动过,结论可能已经不成立)。
写完报告(或确认依据没变)时,用同一条命令加 `--record` 把当前依据的摘要写进报告
(`node …module-report-check.mjs <模块根> --record`,覆盖前留旧版本)。
**只验路径存在与内容摘要,不判内容对不对** —— 那是本技能与审查的事。引用了不存在的东西(比如 IP
换成 XPM 之后,报告还指着老 IP 的卡)就是"看着验过了":要么把证据补出来,要么如实改报告,不许留着。
**已经移除/已退役的东西写成叙述,别写成反引号路径**(写成 `rtl/ip/<老 IP>/…` 这种路径,检查器只会如实
报"这个路径不存在"—— 那是它的职责;叙述里说明"当时…现已移除"就不会误伤)。

测试平台源码、参考模型与比对脚本、本次结果(日志、波形、输出数据)都放 `verif/`,按文件名区分;
不要另建源码目录,也不要只把结果落在这里而把源码留在别处。

本环节只能证明"逻辑符合参照"。时序与上板不在本环节范围内。

## 本环节要跑的命令

按顺序(都是模块级,在 `tools/module/` 下):

| 干什么 | 命令 | 在哪一节 |
|---|---|---|
| 起测试平台 | `node "<自带命令目录>\module\module-verif-new.mjs" <模块根> <模块名> --template "<测试平台模板路径>"` | 第一步 |
| 起仿真脚本 | `node "<自带命令目录>\module\module-verif-new.mjs" <模块根> --kind run-do` | 第二步 |
| 起比对脚本 | `node "<自带命令目录>\module\module-verif-new.mjs" <模块根> --kind comp` | 第四步 |
| 跑出来 | 按选中的仿真器:ModelSim 是 `& "<仿真器路径>" -c -do run.do`(在 `verif/` 下),选了 XSim 就是 `xvlog`/`xelab`/`xsim` 三步 —— 写法都见第二步 | 第二步 |
| 看波形 | 用已经确认过的 `verif/run.do` 起 GUI(XSim 用它的 snapshot),不另起一套加载 | 第三步 |
| **核证据路径** | `node "<自带命令目录>\module\module-report-check.mjs" <模块根>` | 产物(写 `PASS` 之前) |

比对脚本按 spec 约定的格式自己写或复用参考模型,不是一条固定命令 —— 判法见第四步。
