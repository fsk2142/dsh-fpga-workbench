# project-release:发布归档

**只在用户明确要交付/发布时做** —— 实现跑完不等于要发布,不得自动收尾归档。

## 前置

1. 上游环节**都是 `PASS`,或是有依据的 `NOT_APPLICABLE`**(与 `fpga-project-integrate` 的正式验收
   同一条口径;`BLOCKED` / `UNVERIFIED` / `FAIL` 都不算"有结论"):实现(`project/impl/`)、
   时序(`project/timing/`)、要上板的还有上板(`project/board/`)
2. 有产出的 bit / bin / mcs,且知道它是哪一次实现出的
3. 模块版本能从各模块文件头读到(读不到就不算齐,见「版本怎么定」)

## 一句话判据

**照着归档里的东西,能重建出同一版设计** —— 源码、约束、IP、工具版本、脚本、策略(与种子)都对得上,
重建出来的功能与签核结论一致。做不到就不算发布完成。

**别把"能重建"说成"bit 逐字节相同"**:综合/实现本身不保证位级确定性(工具版本、策略、随机种子、
时间戳都可能改变布局)。只有在**真验过**(同一输入重跑并比对哈希)之后才写"逐字节一致",
否则写实话:能重建同一版设计、功能与签核结论一致。

## 归档什么

| 类别 | 具体 |
|---|---|
| 产物 | bit / bin /(固化用)mcs,文件名带版本 |
| 报告 | 实现后的时序摘要、资源占用、DRC 结果 |
| 约束 | 约束文件(XDC)本身,以及管脚对照表的最终版 |
| 可复现 | `write_project_tcl` 导出的工程脚本(建工程、加源、加 IP、跑流程) |
| 源码 | 顶层与各模块源文件的清单 + 版本号(能对上文件头里的版本) |
| 说明 | 本版做了什么、与上一版的差异、已知问题 |

## 版本怎么定

- 顶层文件头里的版本号 = 这一版归档的版本号(不一致就是漏改了)
- 每个模块的版本从它自己的文件头读,**不得凭记忆写**

## 判据

- **PASS**:上面六类齐;工程脚本能重建工程;版本号对得上;已知问题写清楚了
- **FAIL**:缺产物或缺可复现脚本;版本号与文件头不一致
- **BLOCKED**:上游有环节不是 `PASS`、也不是有依据的 `NOT_APPLICABLE`(`BLOCKED` / `UNVERIFIED` /
  `FAIL` 都算)→ 那就**不是发布**,不得强行发布
- **NOT_APPLICABLE**:这次不做发布

## 产物

写 `<工作区根>/project/release/release.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)
  (判定词的含义见 `fpga-module-verif` 的**状态表**,唯一权威)
- 版本号 + 日期 + 对应哪次实现(bit 路径)
- 六类归档物的**实际路径**
- 复现步骤:从干净的工程目录开始,按顺序要跑哪些命令(命令原文)
- 模块版本表:模块 → 版本 → 该模块最后的环节结论
- 已知问题与未验证项

## 不要做的事

- **不得**把 Vivado 工程目录整个塞进归档 —— 它有几个 G,而且大部分能重建;
  归档"重建它的脚本 + 源文件清单"就够了
- **不得**在归档里改报告内容;报告是证据,只读
