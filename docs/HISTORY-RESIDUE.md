# 历史残留清单

本文件记录**本地已清除、但远端可能仍可访问**的旧对象（N-06）。

## 为什么需要它

`git filter-branch` + `git push --force` 只改变「当前 refs 指向哪里」。
GitHub 侧的旧对象**不会立刻消失**：

- 旧 commit SHA 直接 URL（`/commit/<sha>`）在平台回收前仍能打开
- PR / issue 里引用过的旧 SHA 仍可解析
- 别人的 fork / clone 早已把所有对象带走，管不了
- CDN 与对象存储缓存有自己的过期策略

**所以「本地 `git log` 干净」不等于「远端干净」。** 这份清单是给这件事留个账。

## 判断依据

那段路径是 `C:/Users/<名字>/AppData/...`。**名字本身就是公开的 GitHub 用户名**
（仓库 URL 上是 `fsk2142`），所以它**不构成身份泄露**：

- 不暴露真实姓名（除非用户名本身就是）
- 不暴露邮箱（所有提交都用 `users.noreply.github.com`）
- 不暴露任何凭据

**结论：风险等级低，不做平台级清除申请。** 如果将来在历史里发现真实 token 或
非公开的身份信息，那时的处理顺序是：

1. **先吊销/轮换**（改历史不能代替吊销）
2. 走 GitHub 敏感信息移除流程（Support 工单）
3. 记录处理结果与未能控制的范围（fork / 镜像）

## 不要再做的事

- **不要为了"彻底"反复强推同一段历史** —— 每次强推都会产生新的孤儿对象，
  反而增加需要追踪的 SHA 数量。
- **不要指望本地 `gc --prune=now` 影响远端** —— 它只清本地对象库。

## 如何复核

```
npm run privacy:history      # 扫本地可达历史（提交信息 / blob / 邮箱）
```

远端残留只能靠平台 API 逐个查，见 `tools/check-privacy-history.mjs` 的说明。
