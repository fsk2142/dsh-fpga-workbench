# 上板分级流程(L0–L7)

首次上板失败最贵的不是「有 bug」,而是「不知道 bug 在哪」。分级能把
「板子完全不工作」拆成「第 N 级不工作」,定位成本从几天降到几小时。

**每一级都有明确通过判据,不通过就停在那级,不许跳到下一级。**

## 七级与判据

| 级 | 验证内容 | 通过判据 | 失败时优先查 |
|---|---|---|---|
| **L0** | 电源与配置 | `DONE` 拉高;各电源轨电压实测在规格内;静态电流在预期区间 | 配置模式引脚(`M[2:0]`)、配置时钟、上电顺序、比特流 |
| **L1** | 时钟与 PLL | `PLL/MMCM` 锁定信号有效;时钟输出引脚实测频率与设计值一致(误差 < 100 ppm) | 参考时钟是否起振、PLL 反馈分频 |
| **L2** | 复位释放 | 复位同步释放正常;释放后所有状态机处于 IDLE;各模块复位完成标志有效 | 复位极性、复位同步器结构、复位是否覆盖所有寄存器 |
| **L3** | 寄存器读写 | 通过 JTAG/UART 能正确读写全部寄存器;写后读回一致;只读寄存器返回预期常量 | 地址译码、寄存器位宽、总线时序、读写使能 |
| **L4** | 单通道数据通路 | 选定的一条通道端到端跑通;相关错误计数器保持为 0;trace 显示完整流程 | 握手时序、FIFO 深度、位宽匹配 |
| **L5** | 全通道并行 | 所有通道同时工作;无串扰、无资源争用;各通道错误计数器均为 0 | 仲裁逻辑、共享资源冲突、时钟偏斜 |
| **L6** | 满负载与边界 | 最高速率、最长包、最坏背压下,错误计数器仍为 0 | FIFO 深度不足、背压处理缺陷、时序余量不足 |

> ⚠️ **L0 与 L1 绝不允许跳过**
>
> 这两级成本最低、信息量最大,却最常被「反正之前测过了」跳过。
> 而恰恰是它们能区分「板子根本没起来」和「逻辑有问题」,这两种情况的排查路径完全相反。
>
> 跳级的代价:板子不工作时你无法判断是电源、配置、时钟还是逻辑,
> 只能靠反复改代码重新下载来二分。

**L3 之后再说「功能对不对」。** 前面几级都过了,问题才可能真的在业务逻辑里。

## 每级要提前准备的东西

上板当天才想起来准备,实际执行时往往就被省掉了:

| 级 | 提前准备 |
|---|---|
| L0 | 电源测试点位置图;各轨标称值与容差;配置模式跳线设置;比特流与器件型号对应表 |
| L1 | 时钟测试点物理位置;示波器/频率计;各时钟标称频率清单;PLL 锁定信号的观测方式 |
| L2 | 复位信号观测点;各状态机的状态输出寄存器地址;复位完成标志读取脚本 |
| L3 | 寄存器读写脚本;寄存器映射表;每个寄存器的读写测试向量 |

L0–L3 完全可以脚本化,做成开机自检:换板、换比特流都能一键跑,结果可归档对比
「上次是好的,这次坏了」。

## 生成 L0–L3 自检脚本

```
node project-board-selftest.mjs <工程根>
```

生成 `<工程根>/prj/board_selftest.tcl`(含 L0–L3 四段),用 Vivado Tcl 跑:

```
vivado -mode batch -source prj/board_selftest.tcl
```

**为什么是 Tcl 不是 Python**:指南给的骨架用 `pyjnius` 调 `hw_server`,
而本机没装 pyjnius;`vivado.bat` 与 `hw_server.bat` 都在。
寄存器读写本来就是 Tcl API,绕一层 Python 只是多一个失败点。

**用之前必须做的事**:

1. 把所有 `TODO:` 换成本项目真实的值(**寄存器地址全是占位符**)
2. 确认 hw_server 能连上板子
3. **首次使用请在真实板子上跑一遍**:这份 Tcl 是按官方 API 写的骨架,
   **没有在本机真机验证过**(本机没接板子,`open_hw_manager` 跑不起来;
   用 ModelSim 的 Tcl 代跑不可行,见工具文件头)

**判据设计**:任一级 FAIL 就 `exit 1` 停下,不继续后面的级 ——
L0/L1 没过时,后面几级的结果没有意义。

## 脚本检查不了什么

写清边界,避免误以为都覆盖了:

| 项 | 为什么脚本做不了 |
|---|---|
| 电源轨实际电压 | 要万用表或板载 ADC:脚本只能读设计里有对应寄存器的通道 |
| 时钟实测频率 | 要示波器/频率计,或板载频率计数寄存器 |
| 配置模式引脚电平 | 硬件跳线,脚本只能读 `DONE` |
| 上电时序 | 要示波器抓多通道 |

这四项**必须人工测**,脚本只负责能自动化的部分。

## 内建可观测性

上板调试的速度取决于**你能看到什么**,而不是你多聪明。**这是设计输入,写进 SPEC**,
不是出问题后再补的。

### 四类可观测性(按性价比排)

**① 饱和计数器** —— 每一种异常一个计数器,计数到上限就不再增(饱和),避免溢出回绕。

| 计什么 | 为什么 |
|---|---|
| 各模块的错误数 | 一眼看出哪个模块在出错 |
| 丢弃的包/字节数 | 背压或缓冲不足的直接证据 |
| 超时次数 | 死锁与握手的探针 |
| 重传次数 | 链路质量 |

**② 粘滞里程碑位** —— 每个关键流程节点一个 bit,走通就置 1 且不再清。
不用 trace、不占探针、能长时间跑、能捕偶发事件。

**`wrapped` 标志必须有**:为 false 时有效数据是 `0..wr_ptr`,为 true 时全部有效、
从 `wr_ptr` 开始读才是时间顺序。

**③ 心跳** —— 自由运行时钟驱动的计数器,输出到 LED 或寄存器。

| 现象 | 指向 |
|---|---|
| 心跳不闪 + 寄存器读不到 | 配置/电源问题 |
| 心跳不闪 + JTAG 能连 | 设计没加载或时钟没起 |
| 心跳闪但业务不工作 | 时钟正常,读里程碑位定位到具体模块 |

**④ ILA / VIO** —— 见正文「ILA / VIO:改模块,不要加测试端口」。

### 成本与收益

这一项约占总工时 3–5%,但能把上板调试从「周」压到「天」。

**签署判据**:在不重新综合、不接外部仪器的前提下,能回答三个问题:
① 设计当前处于哪个阶段? ② 哪个模块出现了异常? ③ 异常发生前发生了什么?
三个中任何一个答不出,说明可观测性不足。
