# module-review:代码审查

## 三种审法(按用户所需选择)

- **局部审查**:只看一个文件、一个 always 块、一处 CDC —— 改到哪审到哪,随时可做。
- **早期风险审查**:模块还没做完也能审。看不出结论的地方就写"未完成 / 未验证",并指出
  最可能出问题之处 —— 此时的价值在于尽早发现方向问题。
- **整体审查**(`approved` / `changes requested` / `blocked`):通盘看一遍 —— 东西齐不齐、
  对不对。**只有这一种**要求证据齐备 ——
  `rtl`(机械检查)、`verif`(测试平台 + 独立比对)、(要综合的)`synth` 都得有结论。

前两种不要求前置齐备;缺的环节如实标出即可。第三种里若有环节挂着 `BLOCKED` 或完全没有结论,
**不得给 `approved`** —— 如实说明缺什么,把结论定为 `changes requested` 或 `blocked`。

## 审什么(按顺序,不得跳)

1. **对照规格**:`spec` 里的 AC 逐条问"这一条被谁证明了"。**指不到证据的 AC 就是没做**
2. **对照实现思路**:`spec/flow.md` 那张流程图与代码**是否一致** —— 数据通路的级数与并行度、
   状态跳转条件、握手与反压方向、跨时钟处理。代码换了条路而图没改 = 方案没跟上实现,
   须指出(这条同时能看出该图当初是否经用户确认:未确认的图,现在拿它对照是无效的)
3. **RTL 结构**:文件头与九个小节块、命名、复位极性、一个 always 块里有没有混放不相关的信号
4. **时钟与复位**:时钟域怎么划、复位怎么释放、有跨域的地方有没有同步处理
   —— 跨域不得以"观察无异常"作为通过依据
5. **接口**:握手是否成对(valid/ready)、反压时会不会丢数据、首尾边界怎么处理
6. **断言**:要紧的不变量有没有断言(不要求全都有)
7. **参考模型独立性**:有没有 import RTL 或实现细节、有没有直接返回输入
8. **约束**:时钟名与器件配置是否一致、有没有未约束的路径
9. **证据能复现**:每条结论能不能指到文件和行,跑过的命令原文在不在
10. **引用的路径真的在**:跑一次 `node "<自带命令目录>\module\module-report-check.mjs" <模块根>` ——
   它只核"报告与 AC 里写的那些路径在不在"(不判内容)。指不到的、指到已退役 IP 或已经不存在的
   文件上的,就是**"看着验过了"**:当 `changes requested` 记下来,交回实现方补证据或改报告

## 怎么给结论

- **`approved`**:上述每一条都过了,没有未解释的 FAIL
- **`changes requested`**:有具体问题 —— **必须带定位(`文件:行`)与"改什么"**
- **`blocked`**:前置本身不成立(工具没就绪、证据缺失、规格自相矛盾)

**缺证据不等于通过。** 没跑过的检查写"未验证"并说清原因,不许当成过。
**审查者不改代码**:发现问题记录下交回实现方 —— 自行改动会让"谁改的、改完还审不审"
说不清楚。

## 产物

写 `<模块根>/review.md`(**审查是按需能力,不占目录**):

- **结论行**:`结论:APPROVED` / `结论:CHANGES_REQUESTED` / `结论:BLOCKED` 三选一,写成一个词,
  接手的人一眼看到审到哪
- 逐条核对结果(上述九条,一条一行)
- 发现清单,每条:`id`、位置(`文件:行`)、问题、建议怎么改
- 未验证项及原因

正文里用自然语言写同一件事(approved / changes requested / blocked)也可以,但那个词必须同时出现。

工程级的审查报告写 `<用户指定工程目录>/doc/review.md`(同样不占独立目录)。

发现要能一条条改掉。**不得写"整体感觉还行"** —— 那种结论没法执行,也没法复查。

## 审过之后

`approved` = **本模块完成**,可以作为交付物(供他人使用的 IP、库模块),也可以用进工程。

**进不进工程不是本环节决定的事** —— 由工程 spec 的模块清单表定,而且不是每个模块都会走到
工程级。审查只回答一个问题:这个模块自己站不站得住。
