# project-timing:工程级时序

**一份已经存在的 post-route 报告随时可以读**(用户递过来、或 `project/` 里就有),直接分析;
不必先跑一遍实现环节。只有**正式判工程时序通过**时,才要求报告出自当前这版代码、约束状态清楚。

## 前置

1. **读现有报告随时可以**:报告在手就直接分析,不必先跑实现
2. **正式判 PASS** 才要求:报告出自**当前这版代码**、约束文件是最终版、器件与时钟目标清楚
3. 报告来自布局布线后的实现(`project/impl/` 里的 run);没跑过实现就先跑,别拿综合后的估计判

## 和模块级那一关的区别(不得混淆)

模块级那一段时序**在综合环节里**(`fpga-module-synth`:综合门禁 + 综合后时序),不是独立环节:

| | 模块级(`fpga-module-synth` 里那段) | 本环节(工程级) |
|---|---|---|
| 报告来自 | **综合后估计**(没布局布线,`post_synth`) | **布局布线后**(post-route) |
| 时钟来自 | 分析参考周期 | 板级真实约束 |
| 能证明 | 大概能不能收敛 | **能不能上板跑** |

所以模块级那边频率只是观察值;**到了这里,WNS 才是真的算数** —— 因为约束是板子的真实目标,
不是随手填的分析值。

## 判据

- **PASS**:约束的每个时钟 `WNS ≥ 0`(即"满足用户自定的目标",不是某个统一阈值);
  没有未约束路径;没有被静默跳过的约束;CDC 检查干净
- **FAIL**:有违例路径(给出最差的几条:起点 → 终点 → 裕量)、或有时钟没约束上
- **BLOCKED**:实现没跑完 / 报告没生成 / 约束文件本身有问题
- **NOT_APPLICABLE**:这个工程没有可分析的时序路径(例如纯直通)

## 不收敛怎么办

按这个顺序判断,不得一上来就改约束:

1. **看是哪条路径**:判断是跨时钟域、组合逻辑过长,还是扇出过大;找**最差的那几条**,而非总数
2. **判断是设计问题还是约束问题**:约束漏了、时钟写错了 → 改约束;
   逻辑层级太深 → 改设计(插流水、拆逻辑、加寄存器)
3. **确实要加例外**:必须写清理由与谁确认的 —— 例外是"这里不需要按常规收敛",
   并非"让报告变绿"

**绝不得为了让报告变绿去放宽约束。** 那样上板会以更难查的方式失败。

## 本环节要跑的命令

报告已经存在就直接读;要自己跑一遍时,在实现后的工程里跑这几条:

```tcl
report_timing_summary -file <报告路径>
report_timing -max_paths 20 -sort_by slack -file <违例明细路径>
report_clock_interaction -file <时钟交互路径>
report_cdc -file <跨域报告路径>
```

- 违例明细看最差的那几条(`report_timing -max_paths N -sort_by slack`),不必逐条罗列
- 时序报告与约束状态都在 impl run 的报告目录里;命令原文记入 `timing.md`

## 产物

写 `<工作区根>/project/timing/timing.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)+ 报告文件的完整路径
- 时钟清单:名字、周期、WNS、是否约束上
- 未约束路径计数
- 最差几条违例路径的简表(起点/终点/裕量/所属时钟域)
- 用到的例外与理由
- **实测能达到的最高频率**(如果测了):这是"这个设计能跑多快"的事实,不是门禁
