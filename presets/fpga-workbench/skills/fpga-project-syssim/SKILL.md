# project-syssim:工程内仿真验证

目标是用与当前问题直接相关的证据验证工程行为。先复用仍然可信的已有证据,
再补最便宜且能覆盖风险的仿真,不机械重跑固定层级。

- 测试文件与脚本、日志:**`sim/`**(根目录;不放 `src/` 下)
- 仿真器:**设置里选中的那个**(见会话开头「本机 FPGA 工具链」)—— 优先用厂商仿真器
  (Vivado XSim / ModelSim·QuestaSim 那条线),**不得另挑一个**
- 结论:**`doc/syssim.md`**

其余工程技能按需并列或回跳,见 `fpga-project-spec`。

## 前置

1. 相关 RTL 已平铺在 `src/rtl/`(见 `fpga-project-rtl`)
2. 先盘点已有证据:模块库 `verif/`、工程 `src/sim/` 的简单 tb、根 `sim/` 的工程级 tb 及其日志
3. 正式工程级验证仍以根 `sim/` 的实跑为准;模块报告或简单 tb 只能复用为前置证据
4. 仿真器在设置里已就绪;缺工具 → 如实记 `BLOCKED`,不要假装跑过

## 干什么

先复用可信的已有证据,再按当前任务补覆盖:

1. 核对证据对应的代码版本、器件/参数、仿真器与测试输入;对不上就不能复用
2. 在 `doc/syssim.md` 引用证据路径、日期与覆盖内容,明确哪些风险已经覆盖
3. 模块级报告和 `src/sim/` 简单 tb 不替代工程级结果;需要正式工程结论时,必须在根 `sim/` 实跑
4. 从下面三个层级选与当前问题最相关、成本最低的一级开始;任务需要时再向外扩展

### 1. 单元或单模块覆盖

运行与改动直接相关的工程级 `tb_*`;已有模块证据仍新鲜且覆盖充分时可引用,无需无条件重跑。
跑不了的(缺模型、缺库、缺激励)在 `doc/syssim.md` 列明,不要跳过不提。

### 2. 多模块联合覆盖

问题涉及模块边界、背压或 CDC 时,把相关模块接起来仿(子系统/数据通路/接口对):

- 重点看接口:握手、背压、跨时钟、复位顺序、位宽/符号
- 激励优先用真实数据段
- 判「对不对」时拿独立参照比(见 `fpga-module-verif` 的口径);不要拿 DUT 输出当期望

### 3. 顶层或整机覆盖

问题涉及顶层接线、复位释放或端到端行为时,仿顶层/整机链路
(可与 `fpga-project-integrate` 的 elaborate 呼应):

- 覆盖从入口到出口的主通路、时钟复位释放和多模块一起运行的稳定性
- 简单 tb 的结果**不算正式证据**;要进验收链须有独立判据(见 `fpga-module-verif`)

### 4. 跑法(厂商仿真器)

跑法用设置里选中的那个仿真器走。命令写进脚本,在 **`sim/`** 下一次调用,全程命令行;
调用姿势以会话开头的**已就绪**清单为准,不在本技能里重新探测工具:

- **ModelSim / QuestaSim**:同一份 `sim/run.do` 先跑 compile 模式(`vlib` / `vlog`)、再跑 run 模式(`vsim -c` / `run -all` / `quit -f`);**这一份脚本按设置里选中的「仿真脚本」模板抄改**(编译与运行本来就是同一份模板,路径见会话提示;工程级没有 `*-new` 起文件命令,不要对工程根跑 `module-verif-new`)。从工程 `sim/` 跑时把编译脚本 `RTL_DIR` 改成 `{../src/rtl}`(模块布局是 `{../rtl}`);编译与运行**两步**都带上设置里的 ini(`$env:MODELSIM_INI` 或 `INI_OVERRIDE`)。`quit` 与成败 gate 写进 `.do`
- **Vivado XSim**:`xvlog` / `xelab` / `xsim` 三步;**不要跑 `.do`**(那是 ModelSim 方言)

看波形用**已经确认过的那份脚本**起 GUI;不要在 `sim/` 里裸开 GUI 加载设计(dump 会被清零)。

## 判据

- **PASS**:正式工程级 `PASS` 至少一次根 `sim/` 实跑,并执行独立判据且覆盖当前验收范围;
  模块级证据不能单独产出正式 `PASS`,只做证据盘点或局部覆盖时记 `UNVERIFIED`
- **FAIL**:有 tb 跑挂、数据明显不对、握手卡死、断言触发
- **BLOCKED**:仿真器没就绪 / 关键 tb 或激励缺失且补不了
- **UNVERIFIED**:只做了部分级别、或 tb 在但没跑完
- **NOT_APPLICABLE**:这次没有可仿的逻辑(纯粘合且用户认可不仿)

判定词含义见 `fpga-module-verif` 的**状态表**(唯一权威)。简单 tb 过了 ≠ 验证 `PASS`;
要写进验收链的结论,须有独立判据(见 `fpga-module-verif`)。

## 出问题往哪跳

| 现象 | 优先去 |
|---|---|
| 接口对不上、位宽/时钟接错、连不上 | `fpga-project-integrate` |
| 功能/逻辑不对、波形里算法走歪 | `fpga-project-rtl` |
| 激励、比对、tb 自己的问题 | 本技能(改 `sim/` 再跑) |
| 管脚/IO 电平/时钟约束 | `fpga-project-constraints` |
| 机械规范 / 编译器 lint | `fpga-project-lint` |
| 综合失败 | `fpga-project-synth` |

`rtl` / `sim` / `lint` / `synth` / `constraints` 与集成是**并列**的,不要求固定先后。

## 产物

写 `<用户指定工程目录>/doc/syssim.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)
- **复用了哪些**证据:路径、版本/日期、覆盖内容与仍然可信的理由
- **本次测了哪些**:`sim/tb_*` 清单 + 各自命令/结果摘要
- **没测哪些**及原因(缺什么、为什么跑不动或为何已有证据足够)
- 联仿:覆盖的跨模块路径、激励来源、比对方式与结果
- 日志/波形路径;新文件同步 `doc/files.md`

## 不要做的事

- 不要用**第三方/另一套**仿真器替代设置里选中的厂商仿真器
- 不要把模块级库里的完整验证报告当成工程内仿真结果 —— 工程内以 `sim/` 实跑为准
- 不要只跑一个 tb 就写 `PASS` 却不提其它能测没测的
