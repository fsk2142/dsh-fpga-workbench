# project-constraints:约束与管脚

**本环节出错会损伤硬件。** 管脚分配错、IO 电平错,上板可能直接损坏器件或外设 —— 所以这里的
规矩比别处严:**逐条核过,不许"应该是这样"**。

| 东西 | 在哪 |
|---|---|
| 原理图 / 手册 / 管脚表 | **`sch/`**(用户放入,见 `fpga-project-spec` 第 3 步) |
| 约束文件 | **`xdc/`** |
| 时钟目标 / 复位约定 | **`doc/spec.md` 固定小节**(约束与它一致) |
| 结论 | **`doc/constraints.md`** |

不过"严"是**针对要上板的那些约束**,不是每次都把全部管脚重核一遍:

- **起草/分析约束**随时可以做(读 `sch/`、对着器件手册写 XDC、检查现有一致性)。
- **内部逻辑改动**(改算法、改状态机、改位宽)不自动触发重新核管脚 —— 只要对外的管脚、
  电平和时钟没动,原来核过的那份就还算数。
- **真正要上板之前**,对着 `sch/` 与器件规格把受影响的管脚、电压、IO 标准再核一遍(见
  `fpga-project-board`)。

其余工程技能按需并列或回跳,见 `fpga-project-spec`。

## 前置

1. 工程骨架在(`.fpga-workbench.json` 的 `kind` 为 `project`),见 `fpga-project-spec`
2. 器件与封装已定(`doc/spec.md` 固定小节的器件 part)—— 器件没定,IO 标准与可用管脚都无从谈起
3. **`sch/` 里有原理图或管脚表**(没有就是 `BLOCKED`,不得凭接口名猜管脚)
4. 要上板时先看 `doc/timing.md` 是不是 PASS —— 时序没过,管脚核了也不该上板

**集成之后本技能与 `rtl` / `sim` 并列**,可任意顺序做、随便跳转(见 `fpga-project-syssim`)。
**不要把跳转限制死** —— 例如 IP 要 xdc 才建得起来时,先做约束再回头改 RTL/仿真,完全可以;
**综合之前尽量确保 `rtl` / `sim` / `xdc` 三处都是完好的**即可,没有固定次序。

## 做什么

1. **时钟约束**:每个时钟一个 `create_clock`,周期取 `doc/spec.md` 的**时钟目标**
   (不是随手填的整数;与仿真 `CLK_PERIOD` 等自洽)
2. **管脚分配**:**对着 `sch/` 里的原理图**一条一条核 —— 信号名 ↔ 管脚号 ↔ IO 标准 ↔ 上下拉
3. **IO 标准与电平**:电压标准必须与外设一致(原理图上会标);不确定即询问,不得猜测
4. **时序例外**:`set_false_path` / `set_multicycle_path` 每一条都要写**为什么** ——
   例外是"已知这里不用按常规时序收敛",并非"借此消除报错"
5. **约束都放 `xdc/`**:可按板级/接口拆多个文件;加进 `prj/` 那个工程时用**引用**,
   **不得复制**进工程目录
6. **IP 与 xdc 的关系**:有的 IP **必须配上它的 xdc** 才能顺利创建/实现(时钟、引脚、时序例外),
   有的不需要 —— 按该 IP 的文档/例程决定,需要就写进 `xdc/` 并在报告里记明是给哪个 IP 的;
   不确定就问用户或查例程,不要猜

> ⚠️ **XDC 里不能写 Tcl 控制流**(`if` / `source` / `file`)。
> XDC 会 CRITICAL WARNING 后**静默跳过**那条约束,现象是"没有时钟"或管脚没生效 ——
> 不报错,最难排查。
>
> 可复用 Tcl 脚本放 **`prj/` 下的工程脚本目录**,由流程去 `source`,不要塞进 XDC。

## 判据

**先跑机械检查,再人工判读**:

```
node "<自带命令目录>\project\project-constraints-check.mjs" <工程根>
```

它只查**能确定对错**的三类:时钟端口没 `create_clock`、时钟重复定义、管脚分配冲突
(同一 pin 给两端口 / 同一端口给两 pin —— 后者静默覆盖,Vivado 不报错)。

**它不判**(别拿"通过"当约束正确):时钟频率对不对、`set_false_path` 该不该有、
IO 延迟数值是否合理 —— 这些要设计/协议/板级知识,仍按下面人工核。

- **PASS**:机械检查通过,且约束文件被 Vivado 接受(`constraint_status = PASS`);管脚逐条与 `sch/` 原理图核对过;
  时钟与 spec 时钟目标一致;没有未约束的 I/O;每条时序例外都有理由
- **FAIL**:管脚与原理图不符、IO 标准不对、时钟与 spec 不符、有时序例外但没写理由、有未约束的 I/O、
  或机械检查报了冲突
- **BLOCKED**:`sch/` 里拿不到原理图或管脚表 —— 本环节**过不去**,如实说,不得凭接口名猜管脚
- **NOT_APPLICABLE**:这次不涉及新的管脚(比如只改了内部逻辑)

## 产物

写 `<用户指定工程目录>/doc/constraints.md`:

- 结论(`PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `NOT_APPLICABLE`)+ **`xdc/` 下约束文件路径**
  (判定词的含义见 `fpga-module-verif` 的**状态表**,唯一权威)
  · 速记:`PASS`=实测通过有证据 / `FAIL`=观察到真不符 / `BLOCKED`=缺条件做不了 / `UNVERIFIED`=没验或覆盖不足 / `NOT_APPLICABLE`=确不适用(不掩盖无法验证)
- **管脚对照表**:信号名 | 管脚号 | IO 标准 | 来源(`sch/` 里哪份图第几页/哪个连接器)
- 时钟清单:名字、周期(与 spec 一致)、来源
- 时序例外清单:哪条路径、为什么、谁确认的
- 没核到的管脚**列出来**(不得沉默略过)
- 约束文件有增删时,同步 `doc/files.md`(**位置 + 来源**)

## 停下来问用户的时候

- `sch/` 里没有原理图,或者上面标的不清楚
- 同一管脚有两种可能接法
- 原理图与 `doc/spec.md` 的时钟/接口对不上 —— 先问,不要单方面改约束
- 要放宽约束才能收敛 —— 那是设计问题,不是约束问题,先问
