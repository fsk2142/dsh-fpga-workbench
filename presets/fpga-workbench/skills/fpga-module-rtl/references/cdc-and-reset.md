# 跨时钟域与复位：仿真抓不到的那一类

> 这份文档只讲**结构正确性**。功能正确性由仿真验证，但 CDC 与复位跨域的缺陷
> 在任何仿真里都不会暴露 —— 原因在第一节。

## 为什么仿真永远抓不到

CDC 的核心风险是**亚稳态**：源寄存器的输出在目的时钟的建立保持窗口内变化时，
目的触发器可能进入既非 0 也非 1 的中间状态，且恢复时间不确定。

**RTL 仿真不建模这个物理过程。** 在仿真器眼里，两级触发器同步器的行为就是
「延迟两拍、输出一定正确」。所以跑多少激励、覆盖率多高，都不可能复现亚稳态导致的失效。

同一个道理适用于复位跨域：仿真器把复位释放视为**同一时刻**的确定事件，
而真实硬件上不同触发器因布线延迟与时钟到输出延迟不同，会在不同周期退出复位。

**推论**：CDC 与复位跨域无法通过增加仿真解决，只能靠**静态结构检查 + 形式化证明**。
这也是为什么它们必须独立于功能验证流程。

## 复位跨域：最高发的真实缺陷

在大量实际项目里，CDC 相关缺陷最集中的位置**不是数据通路，而是复位信号**。

### 错误写法

```systemverilog
// ❌ 只做异步置位，没有同步释放
always @(posedge clk or negedge rst_n)
  if (!rst_n) q <= 1'b0;
  else        q <= d;
```

多个模块各自这样写，退出复位的时刻可能不同 —— 因为复位信号的传播延迟不同，
且各触发器的时钟到输出延迟不同。此时状态机处于设计上不存在的中间态，
可能直接锁死或产生错误输出。

### 正确写法

```systemverilog
// ✅ 异步置位、同步释放
module reset_sync (
  input  logic clk,
  input  logic rst_async_n,
  output logic rst_sync_n
);
  (* ASYNC_REG = "TRUE" *) logic [1:0] sync;

  always @(posedge clk or negedge rst_async_n)
    if (!rst_async_n) sync <= 2'b00;
    else              sync <= {sync[0], 1'b1};

  assign rst_sync_n = sync[1];
endmodule
```

全设计统一使用 `rst_sync_n`，确保同域内所有触发器**同时**退出复位。
多时钟域设计：**每个时钟域各实例化一个 `reset_sync`**。

### `ASYNC_REG` 不是可选项

它告诉实现工具把这两级触发器放在相邻位置，以缩短布线延迟、降低亚稳态窗口。

**缺少该属性时，即使结构正确，布局后的实际效果也可能不达标。**

验证方式：在实现后的布局报告里检查这两级触发器是否确实相邻。
只有 `set_false_path` 而没有 `ASYNC_REG`，等于「声明了抗亚稳但没给它条件」。

## 多比特跨域：最危险的场景

单个比特跨域，最坏结果是那个比特被采错一拍。

**多比特总线直接跨域，最坏结果是所有比特都采到、但分别来自不同源周期** ——
产生一个在源端从未出现过的组合值。比如计数器从 `0x0FFF` 跳到 `0x1000`，
接收端可能读到 `0x1FFF` 这种「半个旧值 + 半个新值」。

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| 计数器跨域 | 直接对二进制计数器两级同步 | 改**格雷码**，每次只变一位 |
| 地址总线跨域 | 对地址总线逐位同步 | 异步 FIFO，或源端保持稳定后再传有效标志 |
| 配置寄存器跨域 | 多比特并行写入 | **握手**：先写数据，稳定后拉 valid，接收端同步 valid 后一次性采样 |
| 状态编码跨域 | 自然二进制编码 | 独热码或格雷码 |

**多比特数据总线不能用 `set_false_path` 了事** —— 那只是把告警关掉，问题还在。

## 约束要对应到同步方案

最常见的错误：把所有 CDC 路径统一加 `set_false_path`，告警清零了，
但真实违例也被一起豁免。

| 同步方案 | 应有的约束 | 还要检查什么 |
|---|---|---|
| 两级触发器同步器 | `set_false_path`（单比特控制信号） | 同步器声明 `ASYNC_REG`，且两级触发器布局相邻 |
| 异步 FIFO | `set_clock_groups -asynchronous` | 格雷码指针正确；空满标志的生成有无多比特跨域 |
| 握手协议 | 握手信号加 `set_false_path` | 握手本身有超时保护；请求应答配对，避免单边等待死锁 |
| 多比特数据总线 | **必须用格雷码 / 握手 / 异步 FIFO** | 不能直接 `false_path` |

```tcl
# 正确：用时钟组声明异步关系，而不是逐条 false_path
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_100m] \
    -group [get_clocks -include_generated_clocks clk_156m]

# 错误：全局豁免，把真实违例一起放过
# set_false_path -from [get_clocks clk_a] -to [get_clocks clk_b]
```

## 逐条定性的记录格式

CDC 工具的违例**不允许批量豁免**。每条都要归入三类之一并写理由：

| 分类 | 处理 | 记录要求 |
|---|---|---|
| 真违例 | 改设计：加同步器 / 改异步 FIFO / 改握手 | 修改前后结构，以及哪些测试验过 |
| 已知安全 | 保留，加约束并进豁免清单 | **必须写明为什么安全**（如两时钟实际同源、信号运行期恒定） |
| 工具误报 | 进豁免清单 | 写明误报原因（如工具未识别自定义同步器结构） |

```markdown
### CDC-0001 · u_dma/wr_ptr[*] → u_dma/rd_ptr[*]

- **工具报告**：CDC-3，多比特信号跨域
- **定性**：已知安全
- **理由**：读写指针均采用格雷码，每次跨域仅一位变化，接收端两级同步后不会产生中间值
- **验证**：形式化证明「任意时刻指针差异不超过 1」（见 formal/ptr_gray.sva）
- **评审人**：___  **日期**：___
```

## 形式化该证什么

静态检查只能确认「结构上存在同步器」，**不能证明**「同步器之后的状态机不会进入非法状态」。

对复位释放跨域、关键控制信号跨域这两类高风险路径，值得做针对性证明：

```systemverilog
// 证明目标：复位同步释放后，状态机不得进入非法编码
module rst_sync_formal_check (
  input logic        clk_dst,
  input logic [2:0]  state,
  input logic        rst_sync_n
);
  // 合法编码 0..5，6 和 7 为非法
  always @(posedge clk_dst)
    if (rst_sync_n) assert (state <= 3'd5);
endmodule
```

## 签署条件

1. CDC 违例清零，或每条都有书面定性（真违例 / 已知安全 / 工具误报）
2. 所有同步器均声明 `ASYNC_REG`，且经实现工具确认已正确布局
3. 复位跨域全部采用「异步置位、同步释放」，全设计统一
4. 高风险路径（复位释放、关键控制信号）有形式化证明或不少于两级同步结构
5. 多比特数据跨域全部用格雷码 / 握手 / 异步 FIFO，**无直接跨域**

第 1 条里「每条都有定性」是硬要求 —— **批量 waiver 等于没做这项检查**。
